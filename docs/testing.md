# テストの作成方針

このリポジトリでテストを書く、直す、消すときの基準である。
Claude と Codex のどちらが実装するときにも適用し、レビューもこの基準で見る。
テストの目的は、製品の入口から見える振る舞いを守ることにあり、件数や網羅を成果にはしない。

## 何をテストするか

テストは**製品の入口**から書く。
入口とは、フックが送る HTTP の受付、MCP ツール、ダッシュボードの HTTP API と画面、保存ファイルの読み書き、Claude と Codex のプロセスとの入出力を指す。

- モジュール単体のテストは、入口から `require` で到達するモジュールに限る。
  入口から到達しないモジュールは、接続する PR と同じ PR で入れる。
  接続前に単体テストで契約を固めても、接続時に契約が変わってテストを書き直すことになるためである。
- 失敗経路のテストは、信頼境界の外から来る入力にだけ書く。
  信頼境界の外とは、別のプロセス(フック、Claude と Codex、`gh`)、ファイル、HTTP の 3 つである。
  このリポジトリの中の関数呼び出しは信頼する。
  内部の API に対する型違反、thenable や `Symbol.toPrimitive` を持つ値、オブジェクトが凍結されているかの検査、fixture 自身が正しく失敗するかの検査は書かない。
  呼び出し側はこのリポジトリのコードであり、その振る舞いは呼び出し側のテストで確かめるためである。
- 実 runtime でしか確かめられないこと(プロセスの終了と close、再接続、Codex の app-server の応答)は、fixture で代替しない。
  fixture の合格は runtime の証拠に数えない。
  設計資料に書いた実 runtime の確認は、fixture の試験を厚くしても満たされない。

## どう書くか

- 1 ケースに 1 つの振る舞いを書く。
  テスト名は、入力と期待する結果を 1 文で書く。
  同じ契約に対する入力の表は、1 ケースの中の繰り返しで回してよい(例: イベント種別ごとの状態の表)。
  複数のシナリオ ID を 1 ケースに背負わせたり、1 ケースの中で無関係な状態を順に検査したりしない。
- 境界値は超過側を 1 つ書く。
  上限が定数から導けるなら、「ちょうど上限」の検査は書かない。
- Claude と Codex の両方で回すのは、adapter が分岐する箇所だけにする。
  共通コアは 1 回でよい。
- テスト名は日本語で書く。
- 大きさの目安は、1 ケース 30 行、1 ファイル 1,000 行である。
  1 ケースが 40 行を超えるなら、fixture の組み立てが重い印なので、組み立てを見直す。
- 補助コードは `test/support/` に置き、2 つ以上のテストファイルから使うものに限る。
  1 ファイル専用の組み立ては、そのファイルの中に置く。
  `test/helpers/` のような別の置き場は作らない。

## 報告とレビュー

- 報告には件数を書かない。
  「どの入口のどの振る舞いを確かめたか」と、`npm test` の合否を書く。
  「関連 47 件、全体 2,366 件」のような件数は、何を確かめたかを伝えないためである。
- レビューの指摘にテストを足して応えない。
  指摘が契約の欠落なら、先に設計資料の契約を直し、その契約に対するテストを足す。
  契約に無い防御の要求は非対応にする。
- PR のテストの増分が src の増分の 2 倍を超えるときは、PR 本文に理由を書く。
- 適合試験の計画資料には、入口からの操作と観測だけを書く。
  内部モジュールの fixture の条件を計画資料に書くと、その条件がそのまま単体テストの要求になるためである。

## 既存のテストを見直す基準

次に当てはまるテストは消す。
消すときは、同じ振る舞いを入口のテストが守っているかを確かめ、守っていなければ入口のテストに置き換える。

1. 入口から到達しないモジュールだけを対象にしたテスト。モジュールごと接続する PR に移すか、モジュールと一緒に外す。
2. 信頼境界の内側への型違反、thenable、`Symbol.toPrimitive`、凍結の検査。
3. 「ちょうど上限」と「上限 + 1」の対。超過側だけを残す。
4. adapter が分岐しない共通コアを、両 provider で回しているもの。1 回に減らす。
5. fixture や harness 自身の振る舞いを確かめているもの。
6. 1 つのテストファイルからしか使われない harness。そのファイルの中に戻すか、最小の組み立てに縮める。
7. 実 runtime の未確認を補うために足された fixture の試験。
