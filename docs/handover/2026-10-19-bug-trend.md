# 同種の不具合の対応の計画(2026-10-19)

## 決定済みの判断

| 項目 | 決定 | 理由 |
|---|---|---|
| PR の単位 | Issue ごとに 1 つの PR にする | 不具合ごとにクロスレビューとマージの判断を分けるため |

| #592 の読めない保存ファイル | 読み直しても読めなければ、常駐サーバーの起動を失敗にする(開発者が 2026-10-19 に決定) | 保存しない状態で動かすと、MCP の書き込みや PR の登録が成功を返しながら保存されず、利用者が気付けないため |

## 落とし穴

直した不具合の原因は、次の 5 つの型にまとまる。
実装とレビューでは、同じ型を作り込まないかを確かめる。

1. 非同期の順序と競合:await をまたいで、古い結果を照合せずに書き戻す。フックのイベントは呼び出しごとに別のプロセスで送るので、起きた順と届く順が入れ替わる。受けたときに一度だけ行う副作用(終了、配信済み)を、`hookAt` で並べ替えた結果と照合しない。
2. 確かめられない値を確定値に潰す:計算中、期限切れ、結果不明、読み取りの失敗を、「無い」「成功」「失敗」のどれかに倒す。
3. 実行環境とプロバイダーの想定の偏り:`tool_name === 'Bash'` だけを見る、Claude 専用の前提を Codex に当てる、対話のメインセッションだけを想定して委譲や単発の実行を区別しない。
4. 検査と実行のずれ、イベントの取りこぼしによる取り残し:状態を閉じる経路が 1 種類のイベントだけで、取りこぼすと稼働中や待ちのまま残る。
5. 画面の再描画:分岐の早期 `return` や、無効なボタンへの `focus()` で、後ろの戻し先に届かない。

テストは入口から書く。
#591 は `DashboardState` だけのテストで確かめていたので、`afterEvent` を通る本番の順で起きる不具合を見逃した。
