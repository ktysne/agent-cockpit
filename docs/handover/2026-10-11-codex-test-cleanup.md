# Codex 対応のテスト整理の計画(2026-10-11)

集約ブランチ `codex/feature-codex-support` に積まれたテストを、[テストの作成方針](../testing.md)に沿って整理する作業の計画である。
起点は feature の 856c683(PR #380 のマージ)と main の 518b946(PR #350 のマージ)で、数字はこの 2 つの比較である。
main 側(Claude が書いた既存のテスト)の見直しは対象から外す。
main のテストも src の 2 倍の行数があるが、すべて製品の入口から到達するモジュールを対象にしており、今回の問題(未接続のモジュールと防御検査の量産)とは別の話だからである。
Codex 対応の全体の進みは [codex-support.md](https://github.com/ktysne/agent-cockpit/blob/codex/feature-codex-support/docs/handover/codex-support.md) が正本で、この資料はテストの整理だけを扱う。

テスト名からは、次の偏りが読み取れる(feature だけの増分 1,713 件のうち)。

- 拒否、失敗、throw を確かめるものが 514 件(3 割)。
- バイト数、容量、上限の境界を確かめるものが 218 件(1 割強)。
- シナリオ ID(`ID-F05-A01`、`QRC01` など)を題に持つものが 224 件。1 ケースが 5 つの ID を背負うものがある。
- 英語の題が 1,515 件で、日本語の 1,149 件より多い。

補助コード(`test/support/`、`test/helpers/`)は 32 ファイル 8,000 行で、そのうち 1 つのテストファイルからしか使われない harness が 9 ファイル 2,500 行ある。

典型的な過剰の例を挙げる。

- 停止結果 store の読み取りで「4,097 バイト目を stat の後に検出する」ケース。上限の定数から導ける境界を、fake の filesystem で再現している。
- 共通質問サービスの answerPoll に「then メソッドを持つ任意のオブジェクトを渡しても then を呼ばない」ケース。呼び出し側はこのリポジトリのコードで、thenable を渡す経路が無い。
- 容量計算に「`Symbol.toPrimitive` を持つ slot を渡しても強制変換を起こさない」ケース。同上。

## 原因

テストの量は症状で、原因は作業の進め方にある。
別々の原因が 4 つ重なっている。

1. 「fixture で契約を検証した変更を feature に集約し、実 runtime の確認は採用条件に残す」という 2026-10-08 の案 A が、製品に接続しないモジュールを 1 つずつ PR にする流れを作った。各 PR は単体テストで契約を証明するしかなく、接続は後回しになる。
2. 適合試験の計画資料([provider-conformance-testing.md](https://github.com/ktysne/agent-cockpit/blob/codex/feature-codex-support/docs/design/provider-conformance-testing.md))が、機能ごとにシナリオ ID と内部 fixture の条件を増やし続け、それがそのまま各 PR のテストの要求になった。「停止結果 store の独立条件」のような、入口から観測できない条件が資料に書かれている。
3. 信頼境界の内側(このリポジトリの関数呼び出し)に対しても、外部入力と同じ防御の検査を書いている。
4. クロスレビューの往復で、指摘にテストを足して応えている。報告と引き継ぎ資料が「関連 47 件、全体 2,366 件」のように件数を成果として書き、件数が増える方向に作業が向いた。

## 現在地と次にやること

方針文書と計画は PR #384 で main に入り、2026-10-11 に開発者が以下の方針を決定した。
main の変更を feature へ通常 merge する同期 PR を作成中である。
未接続モジュールの一覧作成と削除はまだ始めていない。

同期 PR のレビュー収束後にマージし、feature の最新 head で一覧を作り直す。
削除 PR から先は 1 つずつ作成し、レビューを収束させてマージしてから次へ進む。
すべての追加、修正、削除は [docs/testing.md](../testing.md) に従う。

3 を先にするのは、未接続のモジュールのテストを刈り込んでも、接続時に契約が変わって書き直しになるためである。

harness の縮小と、それを使うテストの削除を別の PR にすると、間の状態でテストが通らないためである。

## 決定済みの判断 (2026-10-11)

| 事項 | 開発者の決定 |
|---|---|
| 未接続モジュールとその専用テスト | 製品の入口から到達しないモジュールと、それだけを対象にしたテストを feature から外す。PoC と同じ方式で削除直前の feature SHA を固定参照に残す。#209 の段階 2〜3 と #313 は製品実装済みではなく設計済みとして扱う |
| 整理を行う時期と後続機能 | 整理を今行う。整理が終わるまで、新規の機能実装 PR は作らない。整理後は未接続モジュールを製品入口へ接続する作業を優先する |
| 整理の実施者 | 到達するモジュールのテストの刈り込みは Codex が行う |
| PR の進め方 | 1 つの PR を作成し、レビューを収束させてマージしてから次の PR に進む。全 PR の base は feature とする |

全体の状態は[Codex対応の計画](codex-support.md)、テストの判断基準は[テストの作成方針](../testing.md)を参照する。削除直前 SHA は削除 PR の作成時に確定し、固定参照と Issue 状態を同じ PR で更新する。

## 落とし穴

- 「到達しない」の判定は `require` の静的な解析で、動的な `require` や設定ファイル経由の読み込みは追っていない。3 に着手するときは、feature の最新 head で判定をやり直し、外す前に `npm test` と常駐サーバーの起動で到達の有無を確かめる。
- feature は 1 日に 20〜30 本のマージが入るので、この資料の数字とファイルの一覧はすぐ古くなる。一覧は資料に書かず、着手時に作り直す。
- Codex の Windows サンドボックスでは `npm test` が `spawn EPERM` で止まる。`npm run test:inprocess` を使い、`test/ensure-server.test.js` の失敗は「子プロセスを起動できないため未確認」と書く([AGENTS.md](../../AGENTS.md)「テスト」)。
- CLAUDE.md と AGENTS.md は同じ内容に保つ。片方だけに方針の参照を足さない。
