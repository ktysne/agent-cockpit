# 共通質問の設定と製品接続の差分案

この資料はIssue #216の残る製品接続を具体化した確認用の案である。
この案の記録だけでは、新しい設定の採用、標準起動への接続、実runtimeの合格を意味しない。
起点は[main同期PR #276](https://github.com/ktysne/agent-cockpit/pull/276)で、既存の[実runtime計画](2026-10-08-runtime-gates.md)の順序を維持する。

## 現在の実装と不足

共通質問サービスには、開発者の設定を読む`getAutoApplySettings`、登録時の有効化記録、適用時の現在設定とbindingの再確認がある。
一方、通常起動からこのサービスを生成するcomposition、設定の保存元、共通質問専用の設定操作は接続されていない。
既存の離席設定を共通質問の有効化へ転用すると、明示有効化の条件が崩れるため、独立した設定として扱う。

所有実行を通常サーバーへ接続する`startNativeInstructionServer`も、通常の起動入口からは呼ばれていない。
専用driverによる実プロセスとHTTP停止の確認は可能だが、通常製品UIから待ちを確認して停止する試験とは区別する。
現在のCodex runnerはnever/read-onlyで、Plan選択と承認policy選択がない。
本物の質問待ちと許可待ちの生成は、#175の能力確認と権限判断を先に行う。

## 確認後に進める差分

| 段階 | 対象 | 変更と完了条件 |
|---|---|---|
| 1 | trusted設定 | 専用設定ファイルと厳密な読み書きを追加する。未設定、破損、未知schemaは自動適用OFF。既存displayと離席設定から有効化を移行しない。 |
| 2 | 共通composition | 既存native構成と同じ登録情報で実行世代を照合し、各サービスの永続storeと配送adapterを重複生成しないfactoryを追加する。質問と指示のjournalは各契約を保つ。生成条件が不足する場合は非構成として扱う。 |
| 3 | 設定の表示と操作 | 既存設定フォームを踏襲した専用opt-inと待ち時間のモックを作り、表示確認後に製品へ反映する。非構成時は有効化できる操作を表示しない。 |
| 4 | source keyと経路所有 | providerの検証済み実行期間とnative request IDの型、有効範囲を両入口で照合する方法を調査する。登録と配送の前にproducerを一つへ確定し、その所有を再起動後も保持する契約を定める。 |

段階1と2は設定保存と注入用factoryの実装であり、標準起動を自動的に切り替えず、横断する二重登録防止の完成とも扱わない。
段階4の証拠を両入口で取得できるまでは、独立した質問として扱い、本文の一致やモデルの任意questionIdで同じ質問と推測しない。
Claudeの既存フック、`decision-answers.js`、離席設定の変更はこの差分へ含めない。
その境界を変えずに排他契約を満たせる仲介点は未確認なので、設計調査として残す。

## 設定の候補

保存先は、製品compositionへ開発者側から渡す`dataDirectory`配下の専用ファイル`common-question-settings.json`を候補とする。
認証情報とtokenは含めず、モデルのMCP登録引数から設定を書き換える口は設けない。

```json
{
  "schemaVersion": 1,
  "autoApply": {
    "enabled": false
  }
}
```

`minimumWaitMs`は省略可能とし、読み込みadapterが既存サービスの下限定数で補ってからサービスへ渡す。
指定した値が下限未満、不正な整数の場合は、enabledの値にかかわらず設定全体をOFFにする。
設定ファイルの所在はtrustedなcomposition引数から決め、HTTPやMCPから任意パスを指定させない。
製品の更新操作は既存のUI秘密値とOriginの照合を使い、設定変更後の現在値をサービスに供給する。
起動時に厳密に読み込んだ設定をメモリーのsnapshotとして保持し、サービスは登録時と適用時にその現在値を参照する。
更新は直列化し、同一ディレクトリの一時ファイルからrenameする原子的な保存が成功した後にsnapshotを置き換える。
失敗した保存は成功と表示せず、直接ファイルを編集した場合は再起動後に反映する。

登録時OFFだった質問は、その後ONへ変えても自動適用しない。
登録時ONでも、適用時にOFFなら自動適用しない。
旧journalの欠落flagをtrueへ補完しない。
新flagを持つjournalは旧binaryが読めないため、rollbackには対応版を使い、journal削除で再送を許可しない。

## 確認すること

- 未作成、破損、未知schema、不正な待ち時間がOFFになること。
- 再起動しても設定が保持され、旧displayと離席設定の意味が変わらないこと。
- 自動適用には離席中であることも必要で、共通設定ONだけでは適用されないこと。
- 登録後のON、適用前のOFF、bindingの失効と回復、手動回答との競合が既存契約どおりであること。
- 原子的保存の失敗、同時更新、再起動時の読み込みと、公開する設定snapshotが一致すること。
- モデル引数が有効化を偽装できず、非構成時に自動適用できないこと。
- 登録情報と配送storeが共有され、同じcommon keyの再試行で二重配送されないこと。
- 横断source keyと永続的なproducer所有を確認するまで、legacy/commonの厳密な二重登録防止を未完了として残すこと。

両providerの実runtime、通常製品MCP入口、設定の移行と利用者への説明を確認するまで、#216を閉じない。
認証、実CLI起動、権限変更は、この計画の確認と同時に成功扱いへ変更しない。

## 開発者に確認してもらう点

独立した既定OFFの専用設定と、構成の共有条件が揃った場合だけサービスを生成する段階1と2を、次の実装範囲としてよいかを確認する。
設定画面は既存フォームを踏襲するモックを別途確認し、source keyとproducerの排他契約は調査結果を提示してから実装する。
新しい実行開始UI、許可応答口、Codexの権限設定の変更は別の判断として残す。
