# agent-cockpit 実装の計画(2026-10-02)

Claude Code デスクトップアプリのセッション状態を内部ブラウザに表示し、開発者の判断をセッションへ返すダッシュボード agent-cockpit を実装する。
起点は `poc/feasibility` ブランチの最新コミット(PoC、GUI のモック、この計画を含む)。
セッションの受付ソケット(cross-session messaging)で回答を送る経路は対象外とする。送信形式が公開文書に無く、試験送信も auto mode の安全判定で拒否されたためである。Artifact をダッシュボードにする案も対象外とする。状態の更新のたびにモデルがツールを呼ぶ必要があり、hooks のイベントも受け取れないためである。

## 現在地と次にやること

- 実現性の確認は終わっている。結果は [docs/poc-results.md](../poc-results.md) にある。
- GUI のモックは [mock/index.html](../../mock/index.html) にある。`preview_start {name: "agent-cockpit-mock"}` で内部ブラウザに開ける。
- 次のセッションは最初に、この計画と poc-results.md とモックを読み、下の表の 1 番から着手する。判断待ちは 2026-10-02 にすべて決定済み。
- リモートは https://github.com/ktysne/agent-cockpit (private)。PoC、モック、この計画は PR #1 で main へ入れる。1 番の作業は PR #1 のマージ後に main から始める。

## 決定済みの判断

| 項目 | 決定 | 理由 |
|---|---|---|
| 全体の構成(2026-10-02) | 127.0.0.1 の常駐サーバー、hooks、MCP ツール、内部ブラウザの組み合わせ | 作業中の内容を hooks で自動的に集められ、トークンを使わない。複数セッションを 1 か所で一覧できる |
| 情報の書き手 | 作業中の内容とサブエージェントは hooks が自動で送る。タスク、完了条件、判断事項、レビューの状況はメインセッションが MCP ツールで書く | モデルが書くのを、モデルにしか分からない情報に限るため |
| 回答を届ける経路(2026-10-02) | 作業中は `PostToolBatch` フックの `additionalContext` で差し込む。待機中は `asyncRewake` を付けた非同期フックが終了コード 2 で終わる仕組みで起こす | どちらも公式に文書化された仕組みで、安全判定にも当たらない |
| 回答の効力 | ダッシュボードの回答は判断材料として扱う。マージ、main への push、破壊的な操作の承認はチャットで行う | フック経由の文脈は、チャットで直接受けた指示と同じ扱いにならないおそれがあるため |
| PR の表示とマージ(2026-10-01) | セッションが作った PR をプロダクトごとにスタック(base と head の連なり)で表示し、ダッシュボードからマージできるようにする。マージは常駐サーバーが開発者の操作を受けて `gh` で直接行い、セッションには結果を知らせるだけにする | 開発者の要望。モデルにマージを指示する形にすると「回答の効力」の決定に反するが、開発者自身の操作を常駐サーバーが代行する形なら、チャットで承認するのと同じ扱いにできる |
| 許可待ちの表示(2026-10-01) | ツールの実行許可を待っているセッションを、`Notification` フックで受けて「許可待ち」として判断事項と並べて出す。許可はダッシュボードからは出さない | 開発者の採用。止まる原因として判断事項より多い。許可を出す口を作ると、別の Web ページや誤操作で危険な操作を通しうるため、表示だけにする |
| 待ち時間と気づける仕組み(2026-10-01) | 許可待ちと判断事項に待ち時間を出し、一定時間を超えたら強調する。種類別の表示では待ちの長い順に並べる。タブのタイトルを `(件数) Agent Cockpit` にする | 開発者の採用。内部ブラウザを裏に回していても気づけるようにするため |
| 前回見てからの変化(2026-10-01) | プロダクトごとに、前回見てから起きたこと(完了したタスク、作られた PR、仮の推奨案で進んだ判断、CI の失敗)をまとめて出し、新しい項目に印を付ける。「既読にする」で消える | 開発者の採用。離れて戻ったときに、何が変わったかをすぐ分かるようにするため |
| CI が通ったらマージの予約(2026-10-01) | スタックの一番下の PR で、マージできない理由が CI 実行中だけのとき、`gh pr merge --auto` で予約できる。予約のあとに push されたら、常駐サーバーが予約を取り消してセッションと画面に知らせる | 開発者の採用。下から 1 つずつ入れるときの待ち時間を減らす。見ていないコミットが自動で入らないよう、確認した head と違えば取り消す |
| 経路の設定(2026-10-01) | サブエージェントとクロスレビューのそれぞれに「既定」「Codex」「Claude」の 3 択を置く。画面には見出しと選択肢の名前だけを出し、効く範囲や稼働中の件数などの説明の文言は添えない。全セッション共通で、次に起動するサブエージェント、次のクロスレビューから効く。指定は開発者が会話で直接指示したのと同じに扱う | 開発者の要望。稼働中のものを途中で切り替えると、作業の途中で担当が変わって結果がまとまらないため、次からにする |
| 指定した経路が使えないとき(2026-10-01) | サブエージェントで GPT を指定していて GPT が使えない(利用上限、ツール側の無効)ときも、クロスレビューで Codex を指定していて Codex が使えないときも、Claude に切り替えて続け、切り替えたことと理由を報告とダッシュボードに出す | 開発者の決定。作業を止めないことを優先する。クロスレビューは cross-review スキルの今の決まり(終了コード 75 で客観サブエージェントへ)と同じ |
| スタックのマージ順(2026-10-01) | マージボタンは base が既定ブランチ(main)の PR、つまりスタックの一番下にだけ出す。上の PR は「下の #N のマージ待ち」と理由を出す | 上の PR を先にマージすると、main ではなく下の PR のブランチへ入ってしまうため |

### 段階 1b の設計(タスクトレイと個別のウィンドウ)

段階 1b は常駐サーバーの読み取りの口(`GET /api/state`)だけを使うので、段階 2 以降と独立に作れる。

**トレイのプロセス**

- Windows に標準で入っている Windows PowerShell 5.1 の `System.Windows.Forms.NotifyIcon` で作る。外部の依存を足さないためである。Electron や npm のトレイ用パッケージは、依存と配布物が大きくなるので使わない。
- `powershell.exe -NoProfile -STA -WindowStyle Hidden -File src/tray/tray.ps1` で起動する。二重に起動しないよう、名前付きミューテックスで 1 つに保つ。
- メニューには「ダッシュボードを開く」(アイコンのダブルクリックと同じ)、「離席中」、「常駐サーバーを再起動」、「終了」を置く。再起動は確認後に、`server.json` の PID のプロセスコマンドラインに同じチェックアウトの `src/server/server.js` が含まれるときだけ停止し、`ensure-server.js` で起動し直す。`server.json` が無いときは停止せずに起動し、起動後にファイルを読めたことを確認する。ダッシュボードは開かず、再起動前に PID があった場合は PID が変わったことを確認して通知する。
- 常駐サーバーが動いていなければ、「開く」のときに Node で常駐サーバーを起動してから開く。起動の判定と排他は、フックと同じ処理(`ensureServerRunning`)を使う。

**個別のウィンドウ**

- Edge のアプリモード(`msedge.exe --app=http://127.0.0.1:<port>/`)で開く。Edge は Windows に標準で入っており、アドレスバーとタブの無い 1 枚のウィンドウになる。
- 既定のブラウザのプロファイルと混ぜないよう、`--user-data-dir` に常駐サーバーの置き場の下の専用のフォルダーを渡す。ウィンドウの大きさと位置は、このプロファイルが覚える。
- 既にダッシュボードのウィンドウがあれば、新しく開かずに前面に出す。ウィンドウはタイトルの末尾が `Agent Cockpit` であることで探す(タイトルの先頭には件数が付く)。

**トレイのアイコンでの通知**

- トレイは 5 秒ごとに `GET /api/state` を読み、許可待ちの件数をツールチップに出し、1 件以上ならアイコンに印を付ける。
- 許可待ちが新しく増えたら、バルーンで 1 回だけ知らせる。押すとダッシュボードを開く。
- 常駐サーバーに接続できないときは、アイコンを灰色にする。
- トレイは `server.json` の PID とポートを読み、離席中の切り替えでは `uiSecret` も使う。イベント用の `secret` は使わない。
- トレイの読み取りも常駐サーバーへの要求に数えるので、トレイが動いている間は常駐サーバーがアイドルで終了しない。

**起動のしかた**

- README に手動で起動する手順を書く。
- ログオン時に自動で起動するには、スタートアップフォルダーにショートカットを置く。リポジトリの外の変更なので、開発者の確認を取ってから行う。

### 段階 1c の設計(離席中の切り替え)

**切り替え**

- 離席中かどうかは常駐サーバーが覚え、`GET /api/state` に含める。常駐サーバーを再起動しても保つよう、置き場に保存する。
- 書き換えは `POST /api/away` で受け、秘密値と Origin を照合する。照合しないと、別の Web ページから自走に切り替えられてしまうため。
- 画面は上部のバーにチェックボックス「離席中」を置く。離席中は上部のバーの色を変えて、切り忘れに気付けるようにする。
- トレイは、右クリックのメニューに「離席中」のチェック項目を置き、離席中はアイコンに印を付ける。

**セッションへの効かせ方**

- `AskUserQuestion` の `PreToolUse` に同期のフックを置き、離席中なら止めて、理由をモデルへ返す。理由には「開発者は離席中。推奨を適用して進め、判断が必要だった事項は最後の報告の『あなたの判断が必要なこと』に書く」と書く。
- 常駐サーバーに届かないとき、または 1 秒以内に答えが無いときは、離席中ではないとみなして止めない。尋ねるほうが安全なため。
- `SessionStart` と `UserPromptSubmit` で、離席中なら `additionalContext` でそのことを文脈に足す。
- 破壊的な操作、PR のマージ、main への push は、離席中でも止まって判断待ちに載せる(グローバルの CLAUDE.md の自走のルールのとおり)。許可のダイアログには答えない。ダッシュボードから許可を出す口は作らない。
- 質問を出して待っているセッションを、離席中にした時点で起こす部分は、段階 3 の届ける経路で足す。

**前提の試作(2026-10-02 に確認済み)**

- 新しく開いた対話のセッションで、`PreToolUse` の matcher に `AskUserQuestion` を書いたフックが、`tool_name: "AskUserQuestion"` と質問の中身(`tool_input.questions`)を受け取って呼ばれた。
- `permissionDecision: "deny"` を返すと、質問の画面は出ず、モデルには `is_error` のツールの結果として `PreToolUse:AskUserQuestion hook error: <permissionDecisionReason>` が返った。
- 実行中のセッションは、途中で書き足した設定のフックを読み込まない。フックは最初に 1 回登録し、離席中かどうかは毎回常駐サーバーに尋ねる作りにする。
- `claude -p` の実行では `AskUserQuestion` が無効なので、この経路は対話のセッションだけで効く。

### 段階 2 の設計(タスク、判断事項、MCP ツール、スキル)

**判断事項の集め方**

- `AskUserQuestion` の質問は、フックで自動で判断事項にする。モデルに同じ内容を 2 回書かせると、手間がかかり、書き忘れも起きるため。
  - `event.js` は `PreToolUse` で `tool_name` が `AskUserQuestion` のときだけ、`tool_input.questions`(質問、見出し、選択肢の label と description、multiSelect)を上限付きで全文送る。常駐サーバーはこれを判断事項にする。`agent_id` が付いたイベントは判断事項にしない。
  - 判断事項の `id` は `tool_use_id` にする。`event.js` と `away.js` は同じ `tool_use_id` を受け取るので、調整なしに同じ判断事項を指せる。
  - 1 回の呼び出しを 1 件の判断事項にし、中に質問の配列を持つ。
  - 推奨の判定は、後述の「回答の入力(画面)」に定める規則を使う。
  - `PostToolUse` で `resolved` にし、`tool_response` の回答を `resolution` に入れる。`PostToolUseFailure` では `withdrawn` として解決済みに畳む。
  - 同じセッションの未解決の判断事項と質問文が一致したら、新しく作らずに既存の判断事項に寄せる。離席中に止められたモデルが、同じ質問を出し直すことがあるため。
- 離席中に `away.js` が止めるとき、理由に判断事項の id を入れ、「推奨で進めたら `cockpit_update_decision` で `provisional` にし、選んだ選択肢を書く」と伝える。
- `AskUserQuestion` を使わずに自分の判断で推奨を適用したものと、チャットの文章で尋ねたものは、モデルが `cockpit_add_decision` で書く。

**判断事項の形**

```
{
  id, session_id, source: "ask" | "mcp",
  state: "waiting" | "provisional" | "resolved" | "withdrawn",
  title, context, questions: [{ question, header, multiSelect, options: [{ label, description, recommended }] }],
  createdAt, updatedAt, resolvedAt,
  answer: { choice, hold, instruction, answeredAt, deliveredAt } | null,
  resolution: { chosen, note } | null,
}
```

- `answer` はダッシュボード(段階 3)が、`deliveredAt` は回答を届けたときに常駐サーバーが、`resolution` はセッション(`PostToolUse` か `cockpit_update_decision`)が書く。書き手が違うので欄を分ける。段階 2 では `answer` は常に `null`。
- `cockpit_add_decision` の判断事項は質問を 1 つだけ持ち、`title` を質問にする。

**タスク**

- セッションごとに `tasks: [{ title, state: "todo" | "doing" | "done", criteria: [{ text, met }] }]` と、最後に書いた時刻を持つ。モデルが一覧を丸ごと置き換える。索引で部分更新させると、古い索引で別の項目を壊しやすいため。

**MCP サーバーとツール**

- `src/mcp/server.js` を stdio の MCP サーバーとして作る。外部の依存は足さず、PoC の `poc/mcp-whoami.js` と同じく JSON-RPC の行を自前で扱う。
- 環境変数 `CLAUDE_CODE_SESSION_ID` と、親プロセスの ID(`process.ppid`)を常駐サーバーに送る。常駐サーバーは `~/.claude/sessions/*.json` の `pid` から session_id を引き直せたらそれを使い、引けなければ環境変数の値を使う。
- 呼ばれるたびに `ensureServerRunning` で常駐サーバーを確かめ、`secret` を付けて `POST /api/sessions/<session_id>/plan` に送る。届かないときは `isError` で「ダッシュボードに書けなかった。作業は続けてよい」と返す。環境変数の値は、結果、ログ、送信に含めない。
- ツールは 3 つにする。説明文は、全セッションの文脈に載るので各 2〜3 文にする。

| ツール | 入力 | 動き |
|---|---|---|
| `cockpit_set_tasks` | `tasks` | タスクの一覧を丸ごと置き換える |
| `cockpit_add_decision` | `title`、`context`、`state: "waiting" \| "provisional"`、`options: [{ label, description, recommended }]` | 判断事項を足し、`id` を返す |
| `cockpit_update_decision` | `id`、`state: "provisional" \| "resolved"`、`chosen`、`note` | 判断事項の状態を変え、`resolution` を書く |

- 書き込みの結果に、保存後の一覧を短く返す(タスクは題と状態、判断事項は id と題と状態)。モデルが自分の認識とのずれに気付けるようにするため。
- 入力は常駐サーバーで検査する。session_id は英数と `-` だけで長さに上限を設ける。題は 200 文字、本文は 2,000 文字、タスクは 50 件、完了条件は 20 件、選択肢は 6 件まで。推奨は 1 つまで。
- `POST /api/sessions/<session_id>/plan` は `/api/events` と同じく、`secret` の照合と Origin が無いことを求める。

**compact と resume**

- `SessionStart` の `source` が `compact` か `resume` のとき、`away.js` が今のタスク(題と状態)と未解決の判断事項(id と題と状態)の要約を `additionalContext` で足す。compact の後のモデルは id を覚えていないため。

**画面**

- セッションのカードに「判断事項」と「タスク」を足す。並びは、モックのとおり、許可待ち、判断事項、今やっていること、サブエージェント、タスクの順にする。止まる原因を上に置くため。
- 判断事項は、状態の印(止めて待っている / 推奨で仮に進行中)、待ち時間、背景、質問と選択肢(推奨に印、説明)を出す。止めて待っているものの待ち時間が 15 分を超えたら強調する。解決済みと取り下げは、終了済みのサブエージェントと同じく折りたたむ。
- タスクは状態の印、「完了条件 n/m」、完了条件の一覧、「最終更新 n 分前」を出す。完了したタスクは折りたたむ。
- 上部の件数に「判断待ち」(`waiting` の判断事項)を足し、タブのタイトルの件数にも含める。トレイのツールチップと通知にも含める。
- 回答の入力(「推奨案で OK」「判断を保留する」、指示欄)は、届ける経路と一緒に段階 3 で足す。

**スキル**

- `skills/agent-cockpit/SKILL.md` に、メインセッションの使い方を書く。
  - 計画を立てたら `cockpit_set_tasks` を呼び、タスクの状態か完了条件が変わったら丸ごと書き直す。
  - 開発者に選ばせる判断は `AskUserQuestion` で尋ねる。推奨の選択肢は label の先頭に「(推奨)」を付け、理由を description に書く。判断事項は自動で記録されるので、別に書かない。
  - 尋ねずに推奨を適用したもの(自走中、離席中に止められたもの)は `cockpit_add_decision` か `cockpit_update_decision` で `provisional` にする。
  - サブエージェントはツールを呼ばない。

**段階 2 から外すもの**

- クロスレビューの状況(モックの「レビュー」欄)。往復の回数や指摘の件数をモデルに数えさせるより、クロスレビューの道具の出力から自動で拾うほうが確かなため。拾い方は段階 5 で決める。
- PR の明示的な登録。使い道が段階 5 なので、段階 5 で足す。

**登録**

- MCP サーバーはユーザーのスコープ(`claude mcp add --scope user`)に、スキルは `~/.claude/skills/agent-cockpit/` に置く。どちらもリポジトリ外の変更なので、手順を README に書き、実施は開発者の確認の後にする。
- 登録の後、MCP の環境の `CLAUDE_CODE_SESSION_ID` とフックの `session_id` が同じ値かを、実際のセッションで確かめる。

### 段階 2a の設計(プロダクト別の構造と表示の操作)

- **セクション**: プロダクト(`product.key`)ごとにセクションを作り、見出しにプロダクト名、ブランチ名、件数のタグ(許可待ち、判断待ち。マージできる PR は段階 5 で足す)を出す。セクションの中に、セッションごとのまとまり(判断事項、今やっていること、タスク、サブエージェント)を並べる。セッションが 1 つならまとまりの見出しを省き、モックと同じ見た目にする。
- **カードの中の並び**: 段階 2 の実装(今やっていること、タスク、サブエージェント)を、モックの順(今やっていること、サブエージェント、タスク)に直す。
- **ブランチ名**: 常駐サーバーがセッションの cwd の `.git/HEAD` を読んで出す(worktree では `.git` ファイルの `gitdir` をたどる)。読めなければ出さない。`git` の子プロセスは起動しない。
- **メインの行**: モックと同じく「メイン」「作業中 / 待機中」の状態の点(作業中は点滅、動きを抑える設定では止める)と、作業中のタスクの題、実行中のツール、経過を 1 行に出す。
- **表示モード**: 主画面の先頭(上部のバーの下)で、プロダクト別と種類別を切り替える。種類別は、許可待ち、判断事項、今やっていること、タスクを種類ごとの一覧にし、各項目にプロダクト名のタグを付ける。並べ替えの操作は種類別に置かない(決定済みの判断「種類別の表示での並べ替え」)。
- **上部の件数のタグ**: モックの 6 種(許可待ち、止めて待っている、仮に推奨案で進行中、保留中、稼働中のサブエージェント、マージできる PR)にそろえる。保留中は段階 3、マージできる PR は段階 5 で数えられるようになるまで出さない。押すとその種類を隠し、取り消し線の表示にして、上に「非表示: …(N 件)」と「すべて表示する」を出す。
- **並べ替え、固定、畳む / 開く**: プロダクトの見出しに上下の移動、最上部への固定、畳む / 開くを置く。固定したものは上にまとめ、固定の境界をまたいで動かす操作は置かない(端では無効にする)。保存は段階 4 で常駐サーバーに行い、それまではブラウザに覚えさせる。
- **接続できないときの表示**: 常駐サーバーから状態を取得できない間は、上部のバーの下に最終取得時刻付きの帯を表示し、取得に成功したら隠す。離席中の切り替えに失敗した場合も同じ帯に 10 秒表示する。

### 段階 2c の設計(表示をモックに揃える)

- **サブエージェントの行**: 種類、作業の説明、状態の点、経過、モデルの札を出す。
  - 作業の説明は、`event.js` が Agent ツールの `PreToolUse` で `tool_input.description` を上限付きで送り、常駐サーバーがサブエージェントに結び付ける。
  - モデルの札は、Claude のモデル(暖色)と、そのサブエージェントが Codex に任せたときの GPT のモデル(緑)を矢印でつないだ 2 段にする。Codex の呼び出しは、起動したイベントの `agent_id` で親のサブエージェントに結び付け、別の行に出さない。モデル名は ID から読みやすい名前にする(例 `claude-sonnet-5-5` を「Claude Sonnet 5.5」)。GPT の札には `codex_home` をマウスを重ねたときの表示で出す。
  - GPT を使わずに Claude 側で実装したときは、GPT の札の代わりに「GPT 不使用(理由)」を出す。理由は `codex-agent: result=` の行と終了コード 75 から取る。背景で動かしてこれらが取れないときは出さない。
  - 「取得元」の文字は出さない。
  - 背景で起動した Codex の終了: 背景で起動した `codex-agent.sh` は、終わったときのフックが届かない。同じ親のサブエージェントのその後のツールの出力(Bash、Read など)に `codex-agent: result=` の行が現れたら、その親が背景で起動した Codex を「終了」にし、行の内容から GPT の札か「GPT 不使用」を決める。この行が見つからないまま親が終わったときだけ「終了未確認」を残す。担当が待たずに終わった場合は、本当に動いている可能性があるため。
- **ツールの行**: ツール名を札にし、中身(コマンド、ファイル)と分けて出す。
- **許可待ちのカード**: 「メイン / <サブエージェントの種類> がツールの実行許可を待っている」、ツールと中身、「N 分待機中」(15 分を超えたら文字の色とカードの背景で示す)を出し、「許可はデスクトップアプリの <セッション> で出す。ダッシュボードからは出せない。」の案内を添える。
- **空の状態の文言**: モックの文言にそろえる。

### 段階 3 の設計(回答を届ける経路と回答の入力)

前提の試作の結果は [docs/poc-results.md](../poc-results.md)。3 つの経路(質問への回答、作業中の差し込み、待機中の起こし)は、どれも実機で届く。

**判断事項の状態と画面**

| 状態 | 意味 | 画面 |
|---|---|---|
| `waiting`(ダイアログ) | 席にいるときに出た質問。デスクトップアプリにダイアログが出ている | 回答欄の代わりに「質問はデスクトップアプリの <プロダクト> のセッションで答える。」 |
| `waiting`(回答待ち) | 離席中に出た質問で、フックがダッシュボードの回答を待っている(`awaitingAnswerUntil` あり) | 回答欄と「あと N 分で推奨に進む」 |
| `provisional` | 推奨で仮に進めた。回答が「保留」なら保留中として数える | 回答欄 |
| `resolved` / `withdrawn` | 解決した、取り下げた | 送った回答の記録だけ |

- 上部の「保留中」は、`waiting` または `provisional` の判断事項のうち、保留回答が無視されていないものを数える。
- 回答待ちの質問は、フックの結末で移る。回答で答えた → `resolved`(PostToolUse)。保留 → `provisional`(保留中。推奨の label で答えるので PostToolUse が届くが、`resolved` にしない)。締め切り、常駐サーバーに届かない → `provisional`。
- `PostToolUseFailure` は lifecycle の上書き状態と待機期限を消す。保留や締切で `provisional` にした判断事項は、その状態を保つ。
- 15 分を超えた強調は、今までどおり `waiting` だけにする。

**回答の入力(画面)**

- モックの回答欄。「推奨案で OK」と「判断を保留する」(どちらか 1 つ、どちらも選ばなくてよい)、指示の欄、「回答を送る」。送った後も変えて送り直せ、最後の回答が効く。
- 送った後の表示は「HH:MM に送信済み: …」、フックへ渡したら「HH:MM に渡した」、セッションが反映したら「HH:MM に反映された」。反映は、回答待ちの質問なら PostToolUse、推奨で仮に進めた判断事項なら、セッションがその判断事項に `cockpit_update_decision` を呼んだこととする。
- 推奨の選択肢は、常駐サーバーが判断事項を作るときに質問ごとに 1 回だけ決める。単一選択の質問で label に「(推奨)」または「(Recommended)」(括弧は全角・半角を許容し、英語の大文字小文字は区別しない)を含む選択肢、または MCP の `cockpit_add_decision` で `recommended: true` を明示した選択肢がちょうど 1 つなら推奨とする。description は判定に使わない。それ以外は推奨なし。推奨の無い質問がある判断事項では「推奨案で OK」を選べなくし、OK で送られる選択肢を回答欄に先に見せる。
- 同じ文の質問を 2 つ含む判断事項は、`answers` の鍵が重なるので、画面からは答えられない(ダイアログの案内と同じ表示にする)。
- 書き込みは `POST /api/decisions/<id>/answer`(`{choice: "ok" | "hold" | null, note}`)で受け、`uiSecret` を照合し、Origin が自分の origin であることを求める(Origin の無い要求は受けない)。

**離席中に出た質問への回答(`away.js` の `PreToolUse`)**

- サブエージェントの中の質問(`agent_id` あり)は、今までどおりすぐ断って推奨で進める。判断事項を作らないため。
- メインの質問は、離席中なら、待ち始めに `{tool_use_id, questions}` を常駐サーバーへ送って回答待ちを登録する(同じ `tool_use_id` なら何度送っても同じ結果)。常駐サーバーは同じ質問の組の判断事項があればそれに束ね、前の回答は新しい回答待ちに使わない。以後は返された判断事項の id で尋ねる。
- 待ち方は long-poll(常駐サーバーが最大 25 秒保持)で、締め切り(登録から 5 分)は常駐サーバーが持つ。poll が途絶えた場合は待ちを解除する。フックの `timeout` は 330 秒にする。
- 常駐サーバーが返す結末と、フックの出力:
  - 回答あり: 常駐サーバーが回答内容を返し、フックは元の `tool_input` に `answers` を加えて出力する。推奨案で OK は推奨の label、指示だけは指示の文、OK と指示は推奨の label に `additionalContext` で指示を添える。
  - 保留: 推奨の label で答え、`additionalContext` に「開発者が判断を保留した。推奨のまま進め、あとで見直せるよう最後の報告に書く」と指示を添える。推奨の無い質問は、離席中が続いていれば締切と同じに扱う。離席中が解除された場合は保留回答を破棄し、ダイアログに戻す。
  - 締め切り: 今までどおり `deny` し、推奨で進める(段階 1c の理由の文)。
  - 離席中が解除された: 何も返さず、ダイアログを出す。
- finish が常駐サーバーに届いた場合、回答済みまたは保留ならその結末を返す。それ以外は離席状態を確認し、離席中が続いていれば `deny` して推奨で進め、判断事項を `provisional` にする。離席中が解除されていれば `released` として何も返さず、ダイアログを出す。
- finish も常駐サーバーに届かなかった場合、フックは離席状態を確認できないため、常に `deny` して推奨で進める。
- フックが 30 秒間 poll しない場合、常駐サーバーは待機期限と届いていた回答を消して待ちを解除する。回答は後から `PostToolBatch` などで差し込まず、判断事項を回答待ち表示からデスクトップアプリのダイアログ表示へ移す。
- フックは終わる前に、自分の結末(answered、timeout、hold、released、server-lost)を常駐サーバーへ送り、常駐サーバーが判断事項の状態を移す。フックの出力からの推測には頼らない。

**推奨で仮に進めた判断事項への回答**

- 常駐サーバーは、セッションごとに渡していない回答と、渡したが反映されていない回答を持つ。届ける文は常駐サーバーが組み立てる: 「開発者がダッシュボードから判断事項 <id>「<題>」に回答した: <推奨案で OK / 判断を保留(推奨のまま進め、最後の報告に書く) / 選択肢を選んだ(質問ごとに「<質問>」は「<label>」。選ばなかった質問は推奨の「<label>」か、推奨が無ければ指示のとおり) / 指示のみ>。指示: <文>。回答に沿って作業を直し、`cockpit_update_decision` で状態を更新する。」
- 作業中: `PostToolBatch` に同期のフックを置く(常駐サーバーに 1 秒以内に尋ねる)。渡していない回答があれば `additionalContext` で差し込み、渡した印を付ける。
- 待機中: `Stop` に `asyncRewake` のフック(`timeout` 3600 秒)を置き、long-poll で尋ねる。渡していない回答があれば stderr に書いて終了コード 2 で終わる(セッションが起きる)。
- 取りこぼしの回収: 渡したが反映されていない回答は、次の `UserPromptSubmit` で `additionalContext` に要約を差し込み直す(1 つの回答につき最大 3 回)。
- `awaitingAnswerUntil` がある質問の回答は `PreToolUse.updatedInput` だけで渡し、`PostToolBatch`、`UserPromptSubmit`、`Stop` の対象から外す。
- `PostToolBatch` と `Stop` のフックは、サブエージェントの中(`agent_id` あり)では何もしない。
- `asyncRewake` のフックはターンの終わりのたびに 1 つずつ起動するので、自分より後の `Stop` か `UserPromptSubmit`、`SessionEnd`、親プロセス(`process.ppid`)の終了で待機を終える。さらに、メインの `PreToolUse`、`PostToolUse`、`PostToolUseFailure` が最後の lifecycle 時刻より新しい場合も待機を終える。最後の lifecycle 時刻より古い `Stop` は世代を進めず、待たずに終わる。
- `SessionStart` で最後の lifecycle 時刻を消すのは source が `startup`、`resume`、`clear` の場合に限る。`compact` では消さない。
- 離席中にした時点ですでにダイアログを出している質問は、外から答えられないので起こさない(段階 1c の「質問を出して待っているセッションを起こす部分」は、この理由で作らない)。

**フックの登録と安全**

- フックは常駐サーバーに自分のイベント名と id を送り、返ってきた JSON を書くだけにする。文言と読み替えは常駐サーバーの 1 か所に置き、テストも常駐サーバーの側で行う。
- `~/.claude/settings.json` に `PostToolBatch` と `Stop`(`asyncRewake`)のフックを足し、`AskUserQuestion` の `PreToolUse` の `timeout` を延ばす。リポジトリの外の変更なので、開発者の確認を取ってから行う。README の手順も直す。
- フックの口は `secret` を照合し Origin の無い要求だけを受け、画面の口は `uiSecret` を照合し自分の origin の要求だけを受ける。セッションの id はフックの入力のものを使い、別のセッションの回答を渡さない。回答の本文は、常駐サーバーのメモリー(保存は段階 4)とフックの出力にだけ置く。
- 実機で確かめること: `Stop` のフックの続けての継続の上限(`CLAUDE_CODE_STOP_HOOK_BLOCK_CAP`)に `asyncRewake` が数えられるか。作業中に `asyncRewake` が終了コード 2 で終わったときに届くか(届くなら `PostToolBatch` は要らない)。

### 段階 3a の設計(タスクの登録を促す)

タスクと完了条件は、メインのモデルが `cockpit_set_tasks` で書いたときだけ出る。書く決まりはスキル `agent-cockpit` にしか無く、使うかどうかはモデルの判断に任されているので、作業中なのにタスクが無いことがある。AI の側が気付くきっかけを、フックで 2 つ足す。画面には何も足さない。

**始めに知らせる**

- `SessionStart` と `UserPromptSubmit` のフックの `additionalContext` に、次の決まりを足す。離席中の知らせを足しているのと同じ仕組みを使う。
  - 作業を始めるときは `cockpit_set_tasks` でタスクと完了条件を登録する。タスクの状態か完了条件が変わったら、一覧全体を書き直す。
  - サブエージェントに渡したときと、その報告を受けたときも書き直す。PR のマージを確かめたときと、作業を切り替えたときも書き直す。
  - 質問への回答だけで終わるような、作業を伴わないターンでは登録しなくてよい。
- サブエージェントの中では足さない(タスクを書くのはメインの決まりのため)。

**作業中に催促する**

- 常駐サーバーは、セッションごとに、メインのツールの使用の回数、サブエージェントの起動と終わり、タスクを最後に書いた時刻を知っている。次のどれかに当たったら、作業中の差し込み(段階 3 の `PostToolBatch` のフック)で催促する。
  - タスクが 1 件も無いまま、今のターン(最後の `UserPromptSubmit` から)でメインがツールを 5 回使った: 「タスクが登録されていない。`cockpit_set_tasks` で今の作業のタスクと完了条件を登録する。」
  - タスクが 1 件も無いまま、メインがサブエージェント(Agent ツール)を起動した: 同じ文。
  - タスクはあるが、サブエージェントの終わりから 10 分たってもタスクが書き直されていない場合、その終了について 1 回だけ: 「サブエージェントが終わった後にタスクが書き直されていない。報告に合わせて `cockpit_set_tasks` で状態を更新する。」
- 同じセッションへの催促は、前の催促から 10 分空ける。タスクが書かれたら、そのセッションの催促の記録を消す。
- サブエージェントの中のツールの使用では催促しない(数えるのはメインのツールだけ)。
- 回数と時間は定数にし、使ってみて調整する。


### 段階 2b の設計(状態不明のセッションへの操作)

「状態不明」は、`~/.claude/sessions/*.json` から動いていると分かるのに、フックのイベントが届いていないセッションである。フックを登録する前に開いたセッションか、常駐サーバーを再起動してからまだ何も操作していないセッションが当たる。

**状態を推定する**

- 状態不明のカードに「状態を推定」のボタンを置く。押すと、常駐サーバーがそのセッションの会話の記録(`~/.claude/projects/<cwd から作る名前>/<session_id>.jsonl`)の末尾を読み、次を返す。
  - 最後に記録が書かれた時刻
  - 最後に使ったツールの名前
  - 入力待ちらしいか(最後の記録がモデルの応答の終わりなら入力待ち、ツールの呼び出しで止まっていれば許可待ちかツールの実行中)
- 会話の記録の形は公開仕様ではないので、読めない、形が違うときは「推定できませんでした」と出し、本体の動きに影響させない。読むのは末尾の一定の大きさ(例えば 256KB)だけにする。
- 会話の本文は画面に出さず、推定の結果だけを出す。会話の記録の場所が `~/.claude/projects/` の下にあることを確かめてから読み、パスを画面から受け取らない(常駐サーバーが session_id と cwd から決める)。
- 推定の結果は、イベントが届いたら消す。 最後の記録の時刻は、今日なら「HH:MM」、今日でなければ「M/D HH:MM」で出す。中断の行で終わる記録は入力待ち、スラッシュコマンドの出力の行(isMeta)は推定に使わない。

**一覧から外す**

- 状態不明のカードに「一覧から外す」のボタンを置く。外したセッションは表示せず、上部に「外したセッション N 件」と「すべて表示する」を出す。
- 外したセッションにフックのイベントが届いたら、自動で一覧に戻す。プロセスが終わったセッションは、今までどおり一覧から消える。
- 外した状態は常駐サーバーが持つ(段階 4 で保存する)。書き込みは画面からの操作なので `uiSecret` と Origin を照合する。

### 許可待ち、待ち時間、前回見てからの変化

- **許可待ち**: `Notification` フックの通知の種類が許可の要求のものを、そのセッションの「許可待ち」として記録する。同じセッションで次の `PreToolUse` か `PostToolUse` が来たら解消とみなす。サブエージェントの中の許可待ちは、`agent_id` があればどのサブエージェントかを出す。受け取れる項目(通知の種類、ツール名、コマンド)は段階 1 の最初に PoC で確かめる。
- **待ち時間**: 常駐サーバーが、判断事項と許可待ちのそれぞれに待ち始めた時刻を持つ。画面は 1 分ごとに表示を更新する。閾値(15 分)を超えたものはカードの背景で強調する。
- **タブのタイトル**: 許可待ちと、止めて待っている判断事項の未回答の件数を出す。0 件ならタイトルは `Agent Cockpit` のまま。
- **前回見てから**: 常駐サーバーが項目ごとに作成時刻と更新時刻を持ち、画面はプロダクトごとに「最後に既読にした時刻」を常駐サーバーへ保存する。そこから後に起きたことを並べる。対象は、完了したタスク、作られた PR、仮の推奨案で進んだ判断、CI の失敗、マージされた PR。新しい判断事項には「新着」の印を付ける。

### 段階 4 の設計(保存と閉じる操作)

- **保存先**: 常駐サーバーは `~/.agent-cockpit/store.json`(`AGENT_COCKPIT_HOME` に従う)に `{version: 1, display, plans, decisionLifecycles, closedTasks, hiddenSessions}` を書く。離席中の状態は今のまま `away.json` に置く。ファイルの権限は 0o600。
- **書き方**: 同じディレクトリの一時ファイルに書いて rename で置き換え、書き込みは 1 本に直列化する。表示の設定、タスク、外したセッションは変更から 500ms まとめて書き、回答の記録(`decisionLifecycles`)は変わったらすぐに書く(配信済みの印を書く前に落ちると、再起動後に同じ答えをもう一度差し込むため)。rename が EPERM や EBUSY で失敗したら 50〜200ms で 3 回まで再試行し、それでも失敗したらメモリーを正として次の変更で書き直す(失敗はログに 1 回だけ出す)。終了時は保留中の書き込みを待つ。トレイの再起動はプロセスを強制終了するので、最後の変更から 500ms 以内のまとめ書きは失われ得る(回答の記録はすぐに書くので残り、rename で置き換えるのでファイルは壊れない。終了を頼む口を足すと書き込みの口が増えるので、足さない)。`away.json` の書き込みも同じ再試行を使う。
- **読み込み**: 読めないファイルと `version` が既知より大きいファイルは `store.json.broken-<時刻>` に退避して空で始める(退避に失敗しても起動は続ける)。読み込み時は回答の記録から `awaitingAnswerUntil` を外し(フックの long-poll は切れているため)、`plans` の判断事項に無い id の記録を捨てる。最終更新から 14 日を過ぎたセッションの記録は捨てる。
- **保存するもの**: MCP で書いたタスクと判断事項(`plans`)、それに付く回答の記録(送信、配信、反映の時刻を含む)、画面で「完了にする」を押したタスク、一覧から外したセッション、表示の設定。
- **保存しないもの**: イベント、イベントから組み立てるセッションとサブエージェントの行、会話の記録からの推定、`decisionOverrides`、終了の判定、秘密値、タスクの催促の内部状態、「終了にする」の記録。
- **再起動で消えるもの**: 離席中の質問(`AskUserQuestion`)から作った判断事項は、イベントから組み立てるので再起動で消える。止まっているセッションへ送った回答が配信前に再起動をまたいだ場合は、`Stop` の待ちが切れているので、次の `UserPromptSubmit` か `PostToolBatch` まで届かない(回答欄には「送信済み」とだけ出て、「渡した」は出ない)。
- **表示の設定**: `{mode, order, pinned, collapsed, hidden}` をスナップショットの `display` で配る。初期値は `null` で、画面はサーバー側が `null` のときだけ `localStorage` の値を送って移す。`POST /api/display` は変えた項目だけを受けてサーバー側で合わせる(トレイのウィンドウと内部ブラウザの古い値で互いを巻き戻さないため)。秘密値と Origin を照合する。テーマは画面ごとの `localStorage` のまま。
- **「完了にする」**: 未完了のタスクに置く。常駐サーバーは `{session_id, title, stateAtClose}` を覚え、スナップショットではそのタスクを完了として出す。セッションがタスクを書き直したとき、同じ題のタスクの状態が `stateAtClose` と違うか、題が無くなっていたら、その記録を消す。題をキーにするため、`cockpit_set_tasks` は同じ題のタスクを並べた一覧を拒む。
- **「終了にする」**: 終了未確認のサブエージェントの行に置く。常駐サーバーは表示している行の `agent_id` をメモリーに覚え、その行を終了として出す。組み立て直した後にその行が終了未確認でなくなるか、稼働中になったら記録を消す(Codex の結果行で確認される場合も拾うため、イベントの種類ではなく組み立てた結果で判定する)。
- **外したセッション**: 保存した記録は、セッションファイルだけで現れる状態不明のセッションに効く。読み込み後の最初のセッションファイルの同期で、ファイルにもタスクにも無いセッションの記録を捨てる。
- **スナップショット**: 保存したタスクがあっても、イベントもセッションファイルも無いセッションは一覧に出さない。フックへ返すタスクの要約(催促の判定に使う)は、保存したタスクをそのまま使う。

### 段階 7 の設計(経路の設定)

モックは [mock/index.html](../../mock/index.html) の上部の「経路の設定」。

**設定の中身と保存先**

- 値はサブエージェント、クロスレビューとも `default`(既定)、`codex`、`claude`。クロスレビューの `claude` は Claude の客観サブエージェントでレビューする。
- 常駐サーバーが `~/.agent-cockpit/routing.json` に保存する。秘密値を含まないので、フックや CLI が常駐サーバーを経ずに直接読める。常駐サーバーが止まっていても、最後の設定が効き続ける。
- 書き換えは、ダッシュボードの書き込みの口(秘密値と Origin の照合あり)からだけ行う。

**サブエージェント**

- 既定は、今の運用のまま(GPT を優先し、利用上限、ツール側の無効、会話での指示があれば Claude)。
- `SubagentStart` フックが `routing.json` を読み、`codex` か `claude` なら、サブエージェントに `additionalContext` で「開発者の指定(agent-cockpit の経路設定): この作業は Claude で行い、codex-agent.sh を呼ばない」のように差し込む。起動時に読むので、稼働中のものには効かず、次に起動するものから効く。
- `claude` のときは、歯止めとして `PreToolUse` フックが `codex-agent.sh` を呼ぶ Bash を拒否し、理由に指定を書く。`codex` は機械的に強制できないので、差し込みとエージェント定義の決まりで守らせる。
- 「会話で直接指示したのと同じに扱う」ために、エージェント定義(`~/.claude/agents/*.md`)か `~/.claude/CLAUDE.md` に「agent-cockpit の経路設定として差し込まれた指定は、開発者が会話で指定したものとして扱い、既定より優先する」と書く。リポジトリ外の変更なので、開発者の確認を取ってから行う。
- 起動時に効いていた設定を常駐サーバーが記録し、画面のサブエージェントの行に出す。表示は「経路: 既定」のように短くし、変更後も稼働中のものには「(変更前)」を添える。
- 「回答の効力」の決定(フック経由の文脈は判断材料にとどめる)の例外になる。許可済みの 2 つの経路のどちらを使うかの選択で、取り消せない操作や外部への操作を含まないため、例外にしてよいと判断した。

**クロスレビュー**

- 既定は、cross-review スキルのとおり(3 択を提示し、推奨の経路で回す)。
- `codex` と `claude` は、スキルの「開発者がレビュアーを指定したとき」と同じに扱う。3 択の提示を省き、指定の経路で回し、報告に「agent-cockpit の設定により Codex(または Claude)で実行」と書く。スキルの決まりどおり、指定が効くのは選択肢 1 と 2 のどちらを使うかだけで、軽微な例外(レビューしない)の判断には影響しない。
- ベンダーで指定する(「別ベンダー」「同ベンダー」でなく、Codex か Claude か)。全セッション共通の設定で、実装者がセッションごとに違っても意味が変わらないようにするため。実装者が Claude なら `codex` は選択肢 1、`claude` は選択肢 2 にあたる。
- レビューの時点で設定を引く。cross-review スキルの 3 択の直前に `node tools/cross-review.js route` を実行し、`routing.json` の指定を出力させる。スキルと `tools/cross-review.js` は ai-cross-review からの vendored なので、変更は upstream に入れて同期する。

### 段階 5、6 の設計(PR の表示とマージ)

モックは [mock/index.html](../../mock/index.html) の「プルリクエスト」欄。rec-studio の #141 をマージすると、付け替えと積み直しの流れを確かめられる。

**どの PR を表示するか**

- セッションが作った PR を、フックで自動的に記録する。`gh pr create` を含む Bash の `PostToolUse` では出力の PR の URL を、GitHub MCP の `create_pull_request` の `PostToolUse` では応答の番号を拾う。
- 記録した PR から base と head をたどり、同じスタックに属するオープンの PR も含める。手で作った PR を途中に挟んでも、スタックが途切れない。
- 段階 2 の MCP ツールに、PR を明示的に登録する口も持たせる。フックで拾えなかった PR の補い用。

**状態の取得**

- 常駐サーバーが `gh pr list -R <owner/repo> --state open --json number,title,url,headRefName,baseRefName,headRefOid,isDraft,mergeable,mergeStateStatus,reviewDecision,statusCheckRollup` を呼ぶ。認証は開発者の `gh` のものを使い、常駐サーバーはトークンを持たない。
- リポジトリが許可するマージ方式は `gh api repos/<owner>/<repo>` の `allow_merge_commit`、`allow_squash_merge`、`allow_rebase_merge` から取り、確認画面には許可された方式だけを出す。
- 取得は 60 秒ごとと、フックで `git push` や `gh pr` を見たとき。画面には最後に取得した時刻を出す。
- 記録した PR が開いている PR の一覧から消えたら、`gh pr view <番号> -R <owner/repo> --json state,mergedAt,mergeCommit,headRefOid` でマージか閉じたかを確かめる。ダッシュボードの外(GitHub の画面など)でマージした PR も、これで拾う。

**スタックの組み立てと、マージできない理由**

- PR の base が別のオープンの PR の head なら、その上に積まれているとみなす。分岐(1 つの PR の上に 2 つ積む)も木として表示する。
- マージできるのは、base が既定ブランチで、ドラフトでなく、コンフリクトが無く、CI が成功し、レビューが承認済みか承認が必須でない(`reviewDecision` が `APPROVED` か空)の PR だけ。できない PR には理由を 1 つ出す。上から順に、base に対応する PR が見つからない、下の PR のマージ待ち、ドラフト、積み直し待ち、コンフリクト、CI、レビューで判定する。
- 常駐サーバーが base を付け替えた PR には「base を <ブランチ> に付け替え済み」の印を出す。付け替えたことは常駐サーバーが記録する(gh の `baseRefName` からは分からないため)。

**マージの手順(常駐サーバー)**

1. 画面の確認欄で、方式とブランチ削除の有無を選んで「マージする」を押す。画面は PR 番号、表示していた head の SHA、方式、削除の有無だけを送る。リポジトリは常駐サーバーが自分の記録から決め、画面からは受け取らない。
2. 常駐サーバーは、秘密値と Origin を照合し、その PR が記録済みのスタックの一番下であることを取り直した状態で確かめる。
3. 上に積まれた PR の base を、先に既定ブランチへ付け替える(`gh pr edit <上の番号> --base main`)。ブランチを先に消すと、上の PR が閉じられることがあるため、順序を守る。
4. `gh pr merge <番号> -R <owner/repo> --<方式> --match-head-commit <SHA>` でマージする。画面を見たあとに push されていたら、GitHub が拒否する。
5. 削除を選んだときは、リモートのブランチを `gh api -X DELETE repos/<owner>/<repo>/git/refs/heads/<ブランチ>` で消す。`gh pr merge --delete-branch` は手元のブランチまで消そうとし、セッションの worktree に触れるので使わない。
6. 予約(`gh pr merge --auto --match-head-commit <SHA>`)のときは、予約した head の SHA を保存する。予約中の PR は通常より短い間隔で状態を取り直し、head が変わっていたら `gh pr merge --disable-auto` で予約を取り消し、画面とセッションに知らせる。取り消しより先にマージされたときは、マージされた head が予約時の SHA と違うことを画面とセッションに知らせる。予約は、承認済みでも承認が任意でもない PR(承認待ち、変更要求)には出さない(条件が揃うまでマージされず、「CI が通ったら」の表示とずれるため)。
   予約は確認画面から「予約を取り消す」で手動でも取り消せる(`gh pr merge --disable-auto`)。
7. 結果を段階 3 の経路でセッションに知らせる。スカッシュかリベースでマージし、上に PR が積まれていたときは「#N が main に入った。上の PR を `git rebase --onto main <旧 base>` で積み直して push する」と依頼を添える。積み直しはセッションの worktree の操作なので、常駐サーバーは行わない。
8. ダッシュボードの外でマージされた PR を状態の取得で見つけたときも、手順 7 と同じ内容を、その PR を作ったセッションへ知らせる。開発者が「マージした」とセッションへ手で伝えなくてよいようにするため。
9. マージ済みの一覧に、PR、時刻、方式、予約による自動のマージかを出し、24 時間で消す。ダッシュボードの外でマージされた PR は、方式が取れないので方式を出さない。

**積み直し待ちの判定**

- スカッシュかリベースでマージした PR の上に積まれていた PR は、下の PR の元のコミットが差分に残る。セッションが積み直して push し、差分から下の PR のコミットが消えるまでは「積み直しが必要」と表示し、マージボタンを出さない。
- 判定は、上の PR の head が、マージした PR の元の head の SHA を祖先に含むかで行う(`gh api repos/<owner>/<repo>/compare/<旧 head SHA>...<上の head>` の `status` が `ahead` か `identical` なら残っている)。マージした時点の旧 head の SHA は常駐サーバーが保存しておく。

段階ごとに、hooks と MCP サーバーを登録する設定の手順(`~/.claude/settings.json` への追記内容)を README に書く。設定の書き換えはリポジトリ外の変更なので、開発者の確認を取ってから行う。

## 落とし穴

- Windows ではフックのコマンドが PowerShell で解釈され、引用符付きの実行ファイルのパスは失敗する。`command` と `args` を分ける exec 形式で書く。
- 常駐サーバーが止まっていても、フックがセッションを止めないようにする。フックは非同期にするか、接続できないときにすぐ終わるようにする。
- `~/.claude/sessions/*.json` は公開仕様ではない。読めなくても本体が動くようにする。
- 内部ブラウザで開くには、常駐サーバーが先に起動している必要がある。SessionStart フックで常駐サーバーを起動し、メインセッションが `preview_start {url}` を 1 回呼ぶ。
- `asyncRewake` のフックはターンの終わりのたびに 1 つずつ起動し、前のものは待ち続ける。後の `Stop` か `UserPromptSubmit` が来たら終わらせる(段階 3 の設計)。
- `AskUserQuestion` の `PreToolUse` のフックが回答を待っているあいだは、デスクトップアプリにダイアログが出ない。待たせるのは離席中だけにする(決定済みの判断「止めて待っている質問への回答」)。
- 拒否や中断(Esc)された `AskUserQuestion` に `PostToolUseFailure` が届くかは未確認である。届かなければ判断事項が `waiting` のまま残るので、実機で確かめてから、`Stop` で取り下げにするかを決める。
- Windows の Bash ツールでは連続する `\` が半分になる(anthropics/claude-code#98622)。バックスラッシュを含むスクリプトはファイルに書いてから実行する。
- `gh pr merge --delete-branch` は手元のブランチも消そうとする。セッションの worktree がそのブランチにいると失敗するか、別の作業を壊す。リモートのブランチは API で消す。
- 上に PR が積まれたブランチを、base の付け替えより先に削除すると、上の PR が閉じられることがある。付け替え、マージ、削除の順を守る。
- `SubagentStart` の `additionalContext` がサブエージェントに届くか、`PreToolUse` の拒否の理由がサブエージェントに伝わるかは未確認である。段階 7 の最初に確かめる。
- `gh` は常駐サーバーの子プロセスとして `execFile`(シェルを通さない)で呼ぶ。ブランチ名や PR 番号を引数に埋めるので、シェルを通すと注入の口になる。
