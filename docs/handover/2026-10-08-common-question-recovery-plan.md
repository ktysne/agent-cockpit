# 保存済み共通質問を隔離して起動する計画

## 現在の問題と確認範囲

[#283](https://github.com/ktysne/agent-cockpit/issues/283)では、保存済み質問が一件でもあると、fresh registryを生成するnative factoryが`question_binding_mismatch`で起動を拒否する。
保存構造の整合性と、現在の実行へ回答を渡せる権限を同じ起動条件として検査しているためである。
#286のfixtureで未選択と選択済みの両方を再現し、拒否時に質問journal、指示journal、checkpointのbyte列が保持されることを確認した。
実Claude/Codex runtimeの結果ではない。

この資料は復旧方式の提案であり、開発者の確認後に実装する。
現在の起動拒否は、この計画の作成だけでは変更しない。
#216の標準起動と設定画面への接続は、復旧実装と関連検証の完了後に別途判断する。

## 開発者に判断してもらうこと

再起動前に保存した質問を、その後も回答できるようにするかを判断する。

| 選択肢 | 利用者から見た動作 | 必要な実装と制約 |
|---|---|---|
| A: 旧質問を隔離し、新しい実行の質問を受け付ける（推奨） | 保存記録を残して起動する。旧質問へ回答や再送はできない。新しい実行で質問を作り直す必要がある。 | 保存構造検査と現在の認可を分離し、旧質問の全操作を遮断する。隔離解除は作らない。 |
| B: 実runtimeで旧要求を再検証し、旧質問への回答を再開する | 未解決であることを証明できた旧質問だけ回答を再開する。証明できない質問は保留する。 | bindingの一致に加え、native要求が未解決である証拠、既存回答と配送履歴、世代と再接続の整合を保証する必要がある。能力調査と別の復旧設計が先に必要。 |

Aは、保存ファイルから実行権限を復元せずに起動不能を解消できるため推奨する。
旧質問への回答を継続する能力は達成しない。
Bを選ぶ場合は、必要な証拠をproviderごとに取得できるかを調査し、その結果を確認してから実装する。

## 推奨案の隔離対象と起動条件

**隔離対象**は、共通質問serviceの初期化時にjournalから読み込んだ全質問である。
同一OS processでserviceを再生成した場合も対象になる。
同じserviceで新規登録した質問は既存契約で処理し、次の初期化時には隔離対象になる。

隔離対象IDをservice内に保持し、journalの既存schemaは変えない。
毎回の初期化で保存済み全件を隔離するため、再起動しても解除しない。
bindingが後から現れた場合も、隔離対象を操作可能へ戻さない。

起動時にはschema、厳密なfieldと型、質問keyの重複、回答digest、配送intent、容量予約を検査する。
質問journalとcheckpointにある配送記録の関連は、保存されたidentity、period、actor、launchRef、配送ID、revisionとdigestを使う独立した整合性検査へ分離する。
この検査は現在のregistryの登録を必要とせず、保存された情報を現在のauthorityへ登録しない。
関連の欠損、改ざん、重複または不正な構造は、引き続き起動拒否とする。

隔離対象にintentがあるのに配送記録がない場合は、intentを保持し、配送を再生成しない。
intentのない配送記録、または存在する記録同士の矛盾は、単純に読み飛ばさない。
新規質問の受付と配送には、既存の現在のwriter認可と最終送信guardを維持する。

## 操作と保存の境界

| 対象 | 隔離された旧質問の扱い |
|---|---|
| 手動回答、自動適用、期限timer | 拒否または対象から除外し、selectionとintentを変更しない。 |
| answer-poll、payload復元、配送再生成 | trustedSinkへ渡す前に拒否し、本文の復元と送信開始を行わない。 |
| 保留と解除、取消、外部解決、応答喪失の通知 | 旧記録を変更する操作は拒否する。隔離だけを外す操作は作らない。 |
| 遅い回答の保存と下書き読出し | 新たな記録の追加と、旧回答を追加指示へ変換する読出しを拒否する。 |
| 同じcommon keyの再登録 | 隔離を解除せず、旧IDを新しいIDへ置き換えない。新しい検証済み実行期間の質問は別keyとして受付可能。 |
| 診断とprojection | 隔離件数、安全な理由コードと操作不可を返す。既存の認可された表示範囲を広げず、native ID、tokenや本文を診断へ追加しない。 |
| 容量と再送防止 | 質問記録、予約量、配送記録と墓標を保持する。隔離しただけでは回収しない。上限時は新規受付を抑止する。 |

隔離対象に対する新規のintent、selection、late answerと配送記録の変更は0回にする。
保存失敗、取得不能、関係の不整合を成功へ読み替えない。
回収と旧質問の再開は、この実装では提供しない。

## 通常指示とshared checkpoint

共通質問の隔離処理は、通常指示の復旧仕様を変更しない。
既存の通常指示serviceは、復旧時に`sending`と`accepted`を`unknown`へ保存する。
そのため、混在checkpointのbyte列が起動前後で常に同じになることは完了条件にしない。

質問の隔離による新規配送とpayload復元は0回に保つ。
通常指示の既存の復旧遷移は許容し、独立した期待値として内容の差を照合する。
質問記録だけを持つfixtureでは質問journalのbyte列保持を確認し、通常指示が混在するfixtureでは既存の安全な遷移以外の変更がないことを確認する。

## 実装するファイルと検証

主な対象は`src/server/common-question-service.js`、必要な保存整合性関数、`src/server/native-instruction-service-integration.js`、対応するserviceとcompositionのテストである。
通常起動、設定画面、モック、legacy hooks、native権限は対象に含めない。
画面の隔離表示と操作状態は後続のモック確認へ残し、今回のAPIは隔離対象の操作を安全に拒否する。

実装時は次のfixtureを両providerのfactoryへ通す。

1. 未選択と選択済みの保存質問があるfresh registryで起動し、旧質問の隔離と新しい検証済み実行の受付を確認する。
2. 旧keyの再登録、手動回答、tick、answer-poll、各変更操作とlate answer読出しを試し、記録変更と配送0回を確認する。
3. 同じbindingの再出現とservice再生成でも隔離が解除されないことを確認する。
4. 配送記録の欠損、孤立、digest不一致、重複、不正schemaと容量予約違反を区別し、不正な構造では起動拒否を維持する。
5. 通常指示のavailable、sending、accepted、unknownが混在する実ファイルで、既存の復旧遷移、質問記録保持と自動再送0回を照合する。
6. 保存失敗、上限到達、初期化失敗と終了時cleanupを確認する。

関連fixture後に統合全体テストを一度実行し、既定の別ベンダークロスレビューで収束させる。
実runtimeの再起動試験はfixtureと別に記録し、未実施を合格へ読み替えない。
#283を閉じる条件は承認した隔離方式の実装と復旧fixtureの成立であり、#216の全体完了とmain採用条件は別に残す。
