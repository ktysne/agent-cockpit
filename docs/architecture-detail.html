図 1　全体の構成

セッション側からの送信 回答・文脈がセッションへ戻る ダッシュボードとの通信 GitHub との通信 ファイルの読み書き 起動・確認など補助の経路

両端に矢印がある経路は、要求への応答で中身が戻ってくることを表す。破線の枠は導入されている場合だけ使う連携。

経路の一覧

行にマウスを重ねると、図 1 の該当する経路が強調される。

番号経路方向使う口・ファイル内容
1イベントの送信event.js → サーバーPOST /api/eventsツールの実行前後、通知、サブエージェントの開始と終了、停止、セッションの終了などを送る。ツールの入力は要約だけを送る。サーバーはここからセッションの状態を組み立て、gh pr create の結果から PR を自動で登録する。
2サーバーの起動確認event.js・MCP → サーバーserver.json、GET /healthserver.json から port と secret を読み、/health で pid と起動時刻が一致するかを確かめる。応答が無ければロックを取ってサーバーを起動する。SessionStart では起動後のダッシュボードの URL を文脈に返す。
3文脈の差し込みaway.js ⇄ サーバーGET /api/away、GET /api/sessions/:id/context離席中であれば「推奨で進める」指示を、入力のたびにタスク登録の決まりを文脈に足す。compact や resume の直後は、登録済みのタスクと未解決の判断事項の要約を取得して足す。
4質問の回答待ちaway.js ⇄ サーバーPOST /api/hooks/answers（ask-*）離席中に限り、AskUserQuestion をダッシュボードで最大 5 分待つ。流れは 図 2 の ④。
5作業中・入力時の回答配信answer.js ⇄ サーバーPOST /api/hooks/answers（post-tool-batch、user-prompt-submit）ツール実行の区切りごとに、届いている回答、PR の通知、タスク登録の促しを文脈へ差し込む。流れは 図 2 の ⑤。
6停止中の回答配信answer.js ⇄ サーバーPOST /api/hooks/answers（stop-*）セッションが止まった後も回答を待ち続け、届いたらセッションを起こして渡す。流れは 図 2 の ⑥。
7経路の差し込みroute.js ⇄ ファイルrouting.json、route-agents/サーバーを介さず設定ファイルを直接読む。サブエージェントの開始時に経路（既定・Codex・Claude）を記録して文脈に足し、終了までその経路を使う。Claude 指定中に codex-agent.sh を呼ぶ Bash は拒否する。
8計画・PR の登録MCP → サーバーPOST /api/sessions/:id/plan、/prsタスクと完了条件の置き換え、判断事項の追加と更新、PR の URL の登録。セッションは環境変数 CLAUDE_CODE_SESSION_ID、無ければ親プロセスの pid と ~/.claude/sessions の対応から決める。
9画面の配信ダッシュボード ⇄ サーバーGET /index.html を返す。画面用の秘密値 uiSecret を meta 要素に埋め込み、画面からの書き込みはこの値を添えて送る。
10状態の取得ダッシュボード ⇄ サーバーGET /api/state2 秒ごとに全体の状態（セッション、タスク、判断事項、PR、離席中、経路の設定、連携の有無）を取得して描き直す。
11画面からの操作ダッシュボード → サーバーPOST /api/decisions/:id/answer ほか判断事項への回答、離席中、経路の設定、表示設定、既読、セッションを一覧から外す、タスクやサブエージェントを閉じる、会話ログからの状態の推定。回答はサーバーの配信待ちに置かれ、③〜⑥ の経路で届く。
12PR のマージ操作ダッシュボード → サーバーPOST /api/pull-requests/merge・reserve・cancel-reservation開発者が確認したマージ、自動マージの予約と取り消し。画面で見た head の SHA を添える。流れは 図 3。
13GitHub 連携サーバー ⇄ GitHubgh CLI登録された PR とその関連 PR、CI、レビューの状態を 60 秒ごとに取得する。マージは gh pr merge --match-head-commit で行う。
14Claude Code の情報の読み取りファイル → サーバー~/.claude/10 秒ごとに稼働中のセッションを検出し、消えたセッションは 60 秒後に終了扱いにする。サブエージェントの定義からモデルを読み、依頼があれば会話ログの末尾から状態を推定する。
15保存と復元サーバー ⇄ ファイル~/.agent-cockpit/起動時に store.json などから復元し、変更は少し待ってまとめて書く。起動ごとに secret と uiSecret を作り server.json に書く。
16クロスレビュー状態の読み取りファイル → サーバーworktree の .cross-review-state.jsonPR を登録したセッションの worktree に ai-cross-review があれば、レビューの状態を読んで PR のカードに出す。無ければ何も出さない。
17サーバーの起動・再起動タスクトレイ → サーバーensure-server.js、/api/state、/api/away起動時にサーバーを確かめて無ければ起動する。メニューの「再起動」は、server.json の pid がこのチェックアウトのサーバーである場合だけ止めて起動し直す。離席中の切り替えもここから送れる。
18画面を開くタスクトレイ → ダッシュボードEdge の --appダッシュボードを独立したウィンドウで開く。ウィンドウを閉じてもトレイとサーバーは動き続ける。

図 2　回答がセッションへ届くまで

ダッシュボードで書いた回答は、サーバーが直接セッションへ送るのではなく、フックが問い合わせて受け取る。セッションの状態によって ④⑤⑥ の 3 通りの受け取り方がある。番号は図 1 と表の番号と同じ。

回答の本文は常駐サーバーのメモリーとフックの出力にだけ置く。許可のダイアログ（パーミッション）には答えない。

図 3　PR の登録からマージまで

P1〜P6 は処理の順番。括弧内の丸数字は、図 1 で使う経路。

モデルにマージを指示する経路は無い。マージは開発者が画面で確認したときだけ、常駐サーバーが gh で行う。

保存先

図 1 の下段の左側。AGENT_COCKPIT_HOME で場所を変えられる。

ファイル書く側読む側中身と扱い
server.jsonサーバーフック、MCP、トレイ（②⑰）pid、port、secret、uiSecret、起動時刻。起動ごとに作り直し、停止時に消す。
store.jsonサーバーサーバー（再起動時）MCP で登録したタスクと判断事項、回答の記録、表示設定、一覧から外したセッション。14 日を過ぎたものは消す。
away.jsonサーバーサーバー（再起動時）離席中かどうかと、その開始時刻。
routing.jsonサーバー（⑪）route.js（⑦）サブエージェントとクロスレビューの経路。読めなければ両方を「既定」とする。
route-agents/route.js（⑦）route.jsサブエージェントごとに開始時の経路を記録する。24 時間使われない記録は消す。
server.logサーバー開発者起動、停止、書き込みの失敗。起動ごとに空にする。

イベントから組み立てるセッションの状態とサブエージェントは保存せず、再起動後のイベントで組み立て直す。

信頼境界

図 1 の常駐サーバーの左右にある破線の帯が、要求を受け付ける 2 つの口。

  • 全体127.0.0.1 だけで待ち受け、Host ヘッダーが 127.0.0.1:port か localhost:port の要求だけを受ける。応答には iframe への埋め込みと別オリジンからの読み取りを塞ぐヘッダーを付ける。
  • フック・MCP 用の口起動ごとに作る secret をヘッダーで照合し、Origin ヘッダーが付いた要求は拒否する。ブラウザーからの要求には必ず Origin が付くため、別の Web ページからイベントや回答を偽造できない。
  • 画面用の口secret とは別の uiSecret を照合し、Origin がダッシュボード自身であることを確かめる。画面から uiSecret が読めても、フック用の口（イベントの送信）は偽造できない。
  • ファイルsecret と uiSecret は server.json にだけ置く。~/.claude/sessions は公開仕様ではないため、読めない項目は黙って飛ばす。
  • 許可許可待ちは表示だけで、ダッシュボードから許可を出す口は無い。
