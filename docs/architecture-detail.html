Agent Cockpit の詳細構成

構成要素、通信経路、保存先までを描いた版。図中の丸数字は、下の表と図 2・図 3 の番号に対応する。表の行か図の丸数字にマウスを重ねると、図の該当する経路だけが強調される。

図 1 全体の構成 経路の一覧 常駐サーバーの内部 図 2 回答の届け方 Claude と Codex の違い 図 3 PR の流れ 保存先 信頼境界 簡易版

図 1　全体の構成

セッション側からの送信 回答・文脈がセッションへ戻る ダッシュボードとの通信 GitHub との通信 ファイルの読み書き 起動・確認など補助の経路

両端に矢印がある経路は、要求への応答で中身が戻ってくることを表す。破線の枠は導入されている場合だけ使う連携。

経路の一覧

行にマウスを重ねると、図 1 の該当する経路が強調される。

番号経路方向使う口・ファイル内容
1イベントの送信event.js → サーバーPOST /api/eventsツールの実行前後、通知、サブエージェントの開始と終了、停止、セッションの終了などを送る。ツールの入力は要約だけを送る。サーバーはここからセッションの状態を組み立て、gh pr create の結果から PR を自動で登録する。Codex のフックは引数 codex 付きで登録し、PermissionRequest と Interrupt も送る。Codex の SessionStart では Codex 本体の pid を探して添え、常駐サーバーの再起動後に行を戻すのに使う。フックの記録（届いたか、所要時間など）は diagnostics として本文に添える。
2サーバーの起動確認event.js・MCP → サーバーserver.json、GET /healthserver.json から port と secret を読み、/health で pid と起動時刻が一致するかを確かめる。応答が無ければ start.lock を取ってサーバーを起動する。SessionStart では起動後のダッシュボードの URL を文脈に返す。Claude と Codex で同じ。
3文脈の差し込みaway.js ⇄ サーバーGET /api/away、GET /api/sessions/:id/context離席中であれば「推奨で進める」指示を、入力のたびにタスク登録の決まりを文脈に足す。compact や resume の直後は、登録済みのタスクと未解決の判断事項の要約を取得して足す。サーバーは起動しない。
4質問の回答待ちaway.js ⇄ サーバーPOST /api/hooks/answers（ask-*）離席中に限り、質問ツール（Claude は AskUserQuestion と ask 付き mcp__ccd_turn__wrap_up、Codex は request_user_input_async と request_user_input）の回答を設定した時間（1〜30 分、既定 3 分）待つ。流れは 図 2 の ④。
5作業中・入力時の回答配信answer.js ⇄ サーバーPOST /api/hooks/answers（post-tool-batch、post-tool-use、user-prompt-submit）ツール実行の区切りごとに、届いている回答、PR の通知、タスク登録の促しを文脈へ差し込む。Codex には PostToolBatch が無いので、PostToolUse から post-tool-use を呼ぶ。流れは 図 2 の ⑤。
6停止中の回答配信answer.js ⇄ サーバーPOST /api/hooks/answers（stop-*）Claude はセッションが止まった後も回答を待ち続け、届いたらセッションを起こして渡す。Codex は同期の Stop で stop-check を呼び、未配信があれば続行させ、離席中だけ回答を待つ。流れは 図 2 の ⑥。
7経路の差し込みroute.js ⇄ ファイルrouting.json、route-agents/サーバーを介さず設定ファイルを直接読む。Claude のフックにだけ登録する。サブエージェントの開始時に経路（既定・Codex・Claude）を記録して文脈に足し、終了までその経路を使う。Claude 指定中に codex-agent.sh を呼ぶ Bash と PowerShell は拒否する。
8計画・PR の登録MCP → サーバーPOST /api/sessions/:id/plan、/prs、/api/diagnosticsタスクと完了条件の置き換え、判断事項の追加と更新、PR の URL の登録、クロスレビューを不要とする記録と保留の記録。起動の報告では、未解決の確認依頼に起動したアプリの URL またはプロセス名を記録し、判断事項の状態は変えない。Claude は、常駐サーバーが MCP の親プロセスの pid と ~/.claude/sessions の対応からセッションを特定し、見つからない場合に環境変数 CLAUDE_CODE_SESSION_ID を使う。Codex は initialize のクライアント名で見分け、tools/call の _meta.sessionId を記録先にする。Codex のフックで登録されていないセッションへの書き込みは 403 で断る。書き込みのたびに、その結果を診断ログへ送る。
9画面の配信ダッシュボード ⇄ サーバーGET /index.html を返す。画面用の秘密値 uiSecret と画面の版を meta 要素に埋め込み、画面からの書き込みは uiSecret を添えて送る。
10状態の取得ダッシュボード ⇄ サーバーGET /api/state2 秒ごとに全体の状態（セッション、タスク、判断事項、PR、離席中、経路の設定、連携の有無、バージョンと新しいバージョンの有無）を取得し、変わっていれば描き直す。画面の版が変わっていれば読み込み直す。
11画面からの操作ダッシュボード → サーバーPOST /api/decisions/:id/answer ほか判断事項への回答、離席中、経路の設定、表示設定（診断ログの記録のレベルを含む）、既読、セッションを一覧から外す、記録の削除、タスクやサブエージェントを閉じる、会話ログからの状態の推定。回答はサーバーの配信待ちに置かれ、③〜⑥ の経路で届く。open-url は https の URL だけを受け、サーバーが既定のブラウザーで開く（マニュアルと PR のリンク）。
12PR の操作ダッシュボード → サーバーPOST /api/pull-requests/merge・reserve・cancel-reservation・conflict-request ほか開発者が確認した即時マージ、レビュー収束後マージの予約と取り消し、衝突の解消の依頼、レビュー不要の設定、マージ結果を閉じる、リポジトリの登録の解除。即時マージは画面で見た head、予約マージは収束記録の head の SHA を照合する。流れは 図 3。
13GitHub 連携サーバー ⇄ GitHubgh CLI登録された PR とその関連 PR、CI、レビューの状態を 60 秒ごとに取得する。PR の作成と push の後にも取り直す。マージは gh pr merge --match-head-commit で行う。
14Claude Code の情報の読み取りファイル → サーバー~/.claude/10 秒ごとに稼働中のセッションを検出し、消えたセッションは 60 秒後に終了扱いにする。状態がイベントから決まらないときは、セッションファイルの busy と idle で補う。利用者がターンを中断したら、会話ログの末尾の中断の行から「中断」と出す。サブエージェントの定義からモデルを読み、依頼があれば会話ログの末尾から状態を推定する。
15保存と復元サーバー ⇄ ファイル~/.agent-cockpit/起動時に store.json などから復元し、変更は 500 ミリ秒待ってまとめて書く。起動ごとに secret と uiSecret を作り server.json に書く。診断ログを書き、⑲ で退避された記録を取り込む。
16クロスレビュー状態の読み取りファイル → サーバーworktree の .cross-review-state.jsonPR を登録したセッションの worktree に ai-cross-review があれば、レビューの状態を読んで PR のカードに出す。PR は別の worktree で作られることがあるので、git worktree list でほかの worktree の記録も候補にする。ツールが無い場合はレビュー不要として扱う。
17サーバーの起動・再起動タスクトレイ → サーバーensure-server.js、/api/state、/api/away起動時にサーバーを確かめて無ければ起動する。5 秒ごとに状態を取得して、待ち件数をアイコンと通知に出す。メニューの「再起動」は、このチェックアウトのサーバーのプロセスだけを止めて起動し直す。離席中の切り替えも uiSecret を添えてここから送れる。
18画面を開くタスクトレイ → ダッシュボードEdge の --appダッシュボードを独立したウィンドウで開き、既にあれば前面に出す。ウィンドウを閉じてもトレイとサーバーは動き続ける。
19届かなかったフックの退避event.js → ファイルdiagnostics/hooks-pending.jsonl常駐サーバーから応答が無かったとき、その記録を退避ファイルに追記する（256 KiB まで）。サーバーは起動時と 10 秒ごとの走査で取り込み、診断ログへ移して消す。
20Codex の情報の読み取りファイル → サーバー~/.codex/（CODEX_HOME）10 秒ごとに session_index.jsonl からスレッド名を読み、セッションの題にする。thread-writer-locks/ のロックが消えた会話は、デスクトップのアーカイブで閉じたものとして 60 秒後に終了扱いにする。保存した Codex 本体の pid が生きていれば、再起動後も行を戻す。
21診断ログの閲覧ダッシュボード ⇄ サーバーGET /api/diagnostics、POST /api/diagnostics・/delete起動の一覧と、選んだ起動の記録を読む。削除は uiSecret が要る。画面の取得や操作が失敗したときも、その記録を送る。
22新しいバージョンの確認サーバー ⇄ GitHubgit ls-remote --tags起動の 60 秒後と、その後 6 時間ごとに agent-cockpit のリポジトリのタグを見る。手元のバージョンより新しいバージョンがあれば、画面に通知と、docs/update.md を指す更新の依頼文を出す。

図 2　回答がセッションへ届くまで

ダッシュボードで書いた回答は、サーバーが直接セッションへ送るのではなく、フックが問い合わせて受け取る。セッションの状態によって ④⑤⑥ の 3 通りの受け取り方がある。番号は図 1 と表の番号と同じ。Codex との違いは各段の下と 次の節 にある。

回答の本文は常駐サーバーのメモリー、store.json の回答の記録、フックの出力にだけ置き、ログには書かない。許可のダイアログ（パーミッション）には答えない。セッションの親プロセスが終われば待ちをやめる。

図 3　PR の登録からマージまで

P1〜P6 は処理の順番。括弧内の丸数字は、図 1 で使う経路。

モデルにマージを指示する経路は無い。マージは開発者が画面で確認したときだけ、常駐サーバーが gh で行う。base が既定ブランチでなければ、マージはマージコミットに固定する。

保存先

信頼境界

図 1 の常駐サーバーの左右にある破線の帯が、要求を受け付ける 2 つの口。

  • 全体127.0.0.1 だけで待ち受け、Host ヘッダーが 127.0.0.1:port か localhost:port の要求だけを受ける。応答には iframe への埋め込みと別オリジンからの読み取りを塞ぐヘッダーを付ける。読み取りの口（GET）は秘密値を照合しないが、このヘッダーで別の Web ページからは中身を読めない。
  • フック・MCP 用の口起動ごとに作る secret をヘッダーで照合し、Origin ヘッダーが付いた要求は拒否する。ブラウザーからの要求には必ず Origin が付くため、別の Web ページからイベントや回答を偽造できない。
  • 画面用の口secret とは別の uiSecret を照合し、Origin がダッシュボード自身であることを確かめる。画面から uiSecret が読めても、フック用の口（イベントの送信）は偽造できない。トレイが送る POST /api/away だけは、Origin の無い要求も受ける。
  • CodexMCP の書き込みは、Codex のフックが登録した終わっていないセッションにだけ受け付ける。Claude の経路の値（親の pid、CLAUDE_CODE_SESSION_ID）と Codex の ID が同じ要求に並んでいたら断る。
  • ファイルsecret と uiSecret は server.json にだけ置く。~/.claude/sessions と ~/.codex のファイルは公開仕様ではないため、読めない項目は黙って飛ばす。
  • GitHub常駐サーバーは起動時に GH_TOKEN などの環境変数を消し、gh 自身のログインを使う。マージは画面の確認からだけ行い、head の SHA を照合する。
  • 許可許可待ちは表示だけで、ダッシュボードから許可を出す口は無い。
