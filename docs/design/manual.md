# 利用者向けマニュアルの構成と画面の撮影

Issue #106 の設計である。
ページの構成、ガイドマップ、ページの部品、検索、組み立て、デモ状態、撮影、配信、検査、画面からの導線を決める。
作りは rec-studio のマニュアル(rec-studio リポジトリの `docs/19-user-manual.md`)にそろえ、この資料には agent-cockpit に合わせて変える点と、rec-studio に無い点を書く。

## 目的

ダッシュボードは表示する情報が多いので、常時表示する項目を厳選し、項目や操作の説明を画面に出さない方針にした(計画書 [2026-10-02](../handover/2026-10-02.md) の決定「画面の常時表示」)。
画面から外した説明と、操作の手順や細かな仕様を引ける場所が要る。

既存の [usage.md](../usage.md) は機能ごとの文章だけで、画面のどこに何があるかを示す図が無い。
説明の指す部品を画面の上で探す手間が掛かるので、部品の名前と位置はスクリーンショットに番号を振った図で示す。
スクリーンショットは画面を変えるたびに古くなるので、撮影の定義から再生成できる生成物として扱い、1 つのコマンドで撮り直せるようにする。

## 前提

- **撮影の元**：実際の常駐サーバーに、隔離した保存先でデモの状態を流し込んだ画面を撮る。モックの HTML は撮らない。実装と画像が食い違わないためである。
- **撮影の手段**：インストール済みの Edge か Chrome をヘッドレスで起動し、Chrome DevTools Protocol(CDP)で操作する。CDP には Node の標準の `WebSocket` でつなぐ。npm の依存を 0 のまま保ち、DOM から部品の矩形を取れるためである。
- **画面の幅**：通常の撮影は、幅 850px のウィンドウで撮る。開発者がダッシュボードを使う想定の幅だからである。
- **配り方**：組み立てたページと画像をコミットし、常駐サーバーが `/manual/` で配る。clone した利用者が組み立てを実行しなくても開けるためである。
- **動画**：作らない。静止画とガイドマップで全ページをそろえ、動画は必要が見えてから別の Issue で扱う。
- **usage.md**：内容をマニュアルへ移して消す。同じ説明を 2 か所に置くと、片方だけが直されて食い違うためである。

## 全体の構成

```
manual/                     原稿と撮影の生成物
├── site.json               ページの一覧と並び、ナビの区分、画面から開く鍵
├── layout.html             全ページ共通のひな形(ヘッダ、ナビ、検索欄、フッタ)
├── pages/*.html            各ページの本文(HTML の断片)
├── assets/                 共通のスタイルとスクリプト
├── shots/*.json            撮影の定義
├── img/<定義名>/           撮影した画像(.png)と部品の矩形(.json)。撮影が生成し、コミットする
└── dist/                   組み立てた結果。組み立てが生成し、コミットする
tools/manual/               組み立て、検査、デモ状態、撮影のスクリプト
```

原稿の置き場は、rec-studio の `site/manual/` に当たる。
agent-cockpit には配布サイトが無いので、リポジトリ直下の `manual/` に置く。

組み立てた結果は `manual/dist/` に置いてコミットする。
rec-studio は結果をコミットしないが、agent-cockpit は clone したまま常駐サーバーを動かす使い方なので、組み立てを利用者の手順に入れないためである。
結果を直接直して原稿と食い違うのは、検査で防ぐ(「検査」)。

画像は `manual/img/` に 1 つだけ置き、`dist/` へは写さない。
同じ画像を 2 か所にコミットすると、撮り直すたびにリポジトリが 2 倍の量で膨らむためである。
常駐サーバーは `/manual/img/` を `manual/img/` から、それ以外を `manual/dist/` から配る(「配信」)。

## ページの構成

### 3 つの層

rec-studio と同じく、説明を役割で 3 つに分ける。

- **ガイド**：画面の名前と位置を示すガイドマップと、目的を達成するまでの流れ。例外と細かな仕様はリファレンスへのリンクにする。
- **リファレンス**：機能ごとに、何ができて、どう操作し、どうなるかを書く。
- **詳細**：境界条件、上限、内部の動き(なぜそうなるか)。リファレンスの各節の末尾に `<details class="more">` で畳む。`<summary>` は「〜の詳細」の形にする。

リファレンスのページは次の決まりで書く。

- ページの冒頭の段落(`lead`)に、そのページで何ができるかを 1〜2 文で書く。
- 節ごとに、最初の段落で「何ができるか」と「どう操作するか」を書き、続く 1〜2 段落で「どうなるか」を書く。
- マージのように取り消せない操作の注意(`note warn`)は、畳まずに本文に残す。読み飛ばすと取り返しが付かないためである。
- 節が画面の部品を扱うときは、節の頭に位置の図を置くか、画面の見方の詳細図へリンクする。

### ページの一覧

入口は `manual/dist/index.html` で、`/manual/` で開く。
各ページは `manual/dist/<id>.html` に組み立てる。

| ナビの区分 | id | 題 | 主な内容 |
|---|---|---|---|
| (入口) | `index` | Agent Cockpit でできること | できること、目的から探す、画面から探す、全ページの一覧 |
| はじめに | `start` | 使い始める | ダッシュボードの開き方、起動と終了、連携(GitHub CLI、claude-codex-bridge、ai-cross-review)の有無で変わる表示。導入の手順は [setup.md](../setup.md) へリンクする |
| はじめに | `screen` | 画面の見方 | 全体図、領域ごとの詳細図、プロダクト別と種類別 |
| 目的別のガイド | `guide-away` | 席を外している間に判断を返す | 離席中にして、判断待ちに回答し、戻ったら「前回見てから」で変化を確かめるまで |
| 目的別のガイド | `guide-stack-merge` | 積み上げた PR を順にマージする | スタックの表示、マージできる条件、レビュー収束後マージの予約、積み直しまで |
| 状況を見る | `work` | タスクと今やっていること | タスクと完了条件、メインの作業行、サブエージェント、更新の無いセッションの隠し方 |
| 状況を見る | `permission` | 許可待ち | 許可待ちの表示、待ち時間、画面から許可を出せない理由 |
| 判断と回答 | `decisions` | 判断事項と回答 | 判断事項の状態、推奨の判定、回答欄、回答の届き方 |
| 判断と回答 | `away` | 離席中 | 離席中の切り替え、回答を待つ時間、締切を過ぎたとき、前回見てから |
| PR | `pull-requests` | PR とマージ | スタックの表示、マージできる条件、確認欄、レビュー収束後マージ、レビュー不要、衝突の解消の依頼、マージの結果 |
| 設定と運用 | `routing` | 経路の設定 | サブエージェントとクロスレビューの経路、効く時点 |
| 設定と運用 | `settings` | 表示の設定 | 設定画面の各項目、表示の操作(固定、並べ替え、畳む、外す、種類の絞り込み)と保存先 |
| 設定と運用 | `tray` | タスクトレイ | 起動、通知、メニュー、ショートカットの作成 |
| 設定と運用 | `server` | 常駐サーバーと保存されるもの | 起動と寿命、再起動、保存先とファイル、再起動で残るものと消えるもの |
| 設定と運用 | `trouble` | 困ったとき | 画面がつながらない、PR が出ない、回答が届かないなど、症状から該当の節へ案内する |

Issue の候補のうち、「画面の見方(上部、プロダクト別、種類別)」は `screen` に、「常駐サーバーの再起動と保存されるもの」は `server` にまとめた。
Issue の候補に無い `work` を足したのは、タスク、作業行、サブエージェントが画面の大半を占めるのに、受け皿のページが無いためである。

#102 で画面から消した説明は、次のページに書く。

| 消した説明 | 書くページ |
|---|---|
| 許可待ちと質問の注記(許可はデスクトップアプリで出す、質問はデスクトップアプリかダッシュボードで答える) | `permission`、`decisions` |
| 回答欄の操作説明 | `decisions` |
| マージの確認欄の説明 | `pull-requests` |
| 経路の説明 | `routing` |

目的別のガイドは、読者が詰まりやすい 2 つの流れに絞る。
離席中の回答と、スタックの順のマージは、どちらも複数の機能をまたぎ、リファレンスを順に読んでも流れが見えにくいためである。

### ガイドのページ

rec-studio の目的別のガイドと同じ形にする。

- 冒頭の段落に、そのガイドで何ができるようになるかを書き、「このページでできるようになること」と「必要なもの」を並べる。
- 流れの段階ごとに節を立て、節の中は手順の部品にし、画面がある手順には手順の画面を置く。
- 例外と細かな仕様は書かず、各手順の末尾からリファレンスの節へリンクする。

## ガイドマップ

画面の部品の名前と位置を、スクリーンショットに番号の札を重ねた図と、番号順の一覧で示す。
札は画像に焼き込まず、HTML で画像の上に重ねる。
画像を撮り直しても札を描き直さずに済み、札と一覧の文字が検索の対象になるためである。
札の位置は、撮影のときに取った部品の矩形から組み立ての時点で決める。

原稿の書式、札と枠の置き方、一覧の書式、図と一覧の連動は rec-studio と同じにする。
ただし、ダッシュボードの画面は rec-studio のような単一の配色ではないので、札の色は次のとおり選び直す。

- 札は、ダッシュボードの状態の色(許可待ちの赤、判断待ちの琥珀、マージできるの緑、稼働中の青、強調の橙)と紛れない紫にする。値はライトとダークの両方の地で、地との明暗差が 4.5:1 以上になるものを組み立ての段階で決める。

### 全体図と詳細図

全体図は、幅 850px のダッシュボード全体に、領域ごとの枠と番号を付ける。
領域は次の 6 つである。

1. ヘッダ(タイトル、離席中、設定のボタン)
2. 件数の札
3. 経路の設定
4. 表示モードの切り替え
5. プロダクトのカード
6. 一覧の最下部(種類の絞り込みの注記、外したセッション、隠したセッション)

詳細図は、領域やカードの中を切り抜いて部品ごとに番号を付ける。
1 枚の番号は 15 個までにする。

| 詳細図 | 載せるページ |
|---|---|
| ヘッダ、件数の札、経路の設定 | `screen` |
| プロダクトのカードの見出し(名前、ブランチ、件数、畳む、固定、並べ替え、外す) | `screen`、`settings` |
| 判断事項のカード(状態、待ち時間、背景、選択肢、回答欄) | `decisions` |
| 許可待ちのカード | `permission` |
| タスクと完了条件、メインの作業行、サブエージェントの行 | `work` |
| PR のスタック(マージできる、条件が残る、積み直し待ち、衝突、レビューの行) | `pull-requests` |
| マージの確認欄 | `pull-requests` |
| 前回見てから | `away` |
| 種類別の表示 | `screen` |
| 設定画面 | `settings` |

状態で見た目が変わる部品は、状態ごとに図を分ける(「表示のパターン」)。

## ページの部品

rec-studio のマニュアルの部品を写して使う。

- 全ページ共通のナビ(左にページの一覧、右に「このページの内容」、末尾に前後のページ、ヘッダに検索欄)
- ガイドの冒頭の「このページでできるようになること」と「必要なもの」
- 手順の部品と手順の画面
- 節の頭に置く位置の図
- 注記(ヒント、注意)
- 詳細の層を畳む `<details class="more">`
- 押すと拡大する画像

配色は、ダッシュボードの配色トークン(`src/web/index.html` の `:root` と `[data-theme]`)を写して使う。
ページの配色は、ダッシュボードの「配色」の設定(`localStorage` の `agent-cockpit.theme`)に従い、設定が無いか読めなければ OS の設定に従う。
マニュアルは常駐サーバーと同じ origin で配るので、ダッシュボードの設定を読めるためである。

rec-studio はショートカットキーの部品(キーキャップ、`gm-keys`)を使うが、ダッシュボードにはショートカットキーが無いので写さない。

## 全ページの検索

rec-studio と同じにする。
組み立ての時点で、全ページの見出し、本文、ガイドマップの項目名から節単位の索引を作り、`manual/dist/assets/search-index.js` に出す。
英数字の全角と半角、大文字と小文字を同一視し、空白で区切った語は AND 条件で扱う。

## 原稿の組み立て

原稿は HTML の断片で書き、依存パッケージを使わない Node のスクリプト(`tools/manual/build.js`)で組み立てる。
rec-studio の `build.js` と `guide-map.js` を写し、置き場とナビの区分を変える。

- `npm run manual:build` で `manual/dist/` を作り直す。
- 組み立ては、同じ原稿と画像から同じバイト列を出す。日時や乱数をページに埋めない。検査が、組み立て直した結果とコミットした結果を比べるためである。
- `site.json` の `pages` は `id`、`source`、`title`、`navGroup` をページ順に持つ。出力先は `<id>.html` に固定する。

## デモ状態

撮影のたびに、隔離した保存先で常駐サーバーを起動し、デモの状態を流し込む。
開発者が普段使っている常駐サーバー、`~/.agent-cockpit/`、`~/.claude/` には触れない。

### 起動

`tools/manual/demo-server.js` が、`startServer` を同じプロセスで呼んで起動する。
コマンドの引数ではなく関数の引数で次を渡せるので、常駐サーバーのコードを撮影のために変えずに済む。

| 引数 | 渡すもの |
|---|---|
| `homeDir` | 一時ディレクトリの下の保存先 |
| `claudeHome` | 一時ディレクトリの下の偽の Claude のホーム。`sessions/*.json` にデモのセッションを置き、`pid` には撮影のプロセスの pid を書く。生きているセッションとして読ませるためである |
| `port` | 0。空いているポートで待ち受ける |
| `pullRequestOptions.execFileImpl` | 偽の `gh`(「偽の gh」)。マージの処理も `PullRequestTracker` を通して `gh` を呼ぶので、この 1 つで足りる |
| `codexAgentScriptExists`、`crossReviewToolExists` | 連携の有無。撮る画面ごとに切り替える |
| `openExternalUrl` | 何もしない関数。撮影中に外部のブラウザを開かないためである |

### 時計の固定

待ち時間や「1 分以内」のような経過の表示は、記録の時刻と今の時刻の差から作るので、そのままでは撮るたびに画像が変わる。
撮り直しで変化の無い画像を書き換えないよう、常駐サーバーとブラウザの両方の時計を固定する。

- 常駐サーバー:`demo-server.js` が、サーバーのモジュールを読む前に、`Date` を時計を差し替えられる版に置き換える。シナリオの各手順は「基準時刻から何分前」の時刻で送り、手順の間で時計を進める。`setTimeout` などのタイマーは置き換えない。
- ブラウザ:`Page.addScriptToEvaluateOnNewDocument` で、ページのスクリプトより先に `Date` を基準時刻に固定する。

基準時刻は、曜日や月をまたがない平日の日中の固定の値にする。

### 流し込み方

デモの状態は、フックと MCP サーバーが使うのと同じ口(`/api/events`、`/api/sessions/<id>/plan`、`/api/sessions/<id>/prs`)へ送って作る。
`store.json` を直接書かないのは、保存の形式が変わったときにデモが黙って壊れるのを避け、実装と同じ経路で画面を組み立てるためである。
画面での操作が要る状態(回答欄に入力した、確認欄を開いた)は、撮影の手順で画面を操作して作る。

デモの内容は `tools/manual/demo/` にシナリオとして置く。
1 枚の全体図に多くの要素が並ぶよう、基本のシナリオは次を含める。

- プロダクトを 3 つ(1 つは複数のセッション)
- 回答待ちの判断事項(推奨あり、複数選択、指示つき)、仮適用した判断事項、解決済みの判断事項
- 許可待ち(長く待たせている閾値を超えたものを含む)
- タスクと完了条件(作業中、未着手、完了)
- メインの作業行(作業中、待機中)と、稼働中と終了済みのサブエージェント(Claude と Codex の経路)
- PR のスタック(マージできる、条件が残る、積み直し待ち、衝突、ドラフト、レビュー未実施、レビュー不要)
- 離席中の期間に起きた変化(前回見てから)

プロダクト名、ブランチ名、タスクの題は、実際の使い方を思い浮かべられる架空のものにし、実在の人名や組織名は使わない。

### 偽の gh

PR の取得とマージは `gh` を子プロセスで呼ぶ。
`PullRequestTracker` は `execFileImpl` を差し替えられるので、シナリオの PR の定義から `gh` の応答を返す関数を渡す。
応答を返すのは、取得に使う `pr list`、`pr view`、`api repos/<owner>/<repo>`、`api repos/<owner>/<repo>/compare/...` と、撮影でマージの結果を見せるときの `pr merge`、`pr edit`、ブランチの削除である。
定義に無い呼び出しはエラーにして撮影を止める。
取得の作りが変わったときに、偽の応答が黙って古いまま画像を作るのを避けるためである。

クロスレビューの状態は、常駐サーバーが worktree の中の `tools/cross-review.js` と状態ファイル(`.cross-review-state.json`)から読む。
デモは一時ディレクトリの下にプロダクトごとの作業ディレクトリを作り、そこにこの 2 つと `.git/HEAD` を置く。
セッションの `cwd` はこの作業ディレクトリを指す。

## スクリーンショットの撮影

### 撮影の定義

撮影の定義は `manual/shots/<定義名>.json` に書く。

```json
{
  "title": "判断事項の回答欄",
  "scenario": "basic",
  "window": { "width": 850, "height": 900 },
  "theme": "dark",
  "integrations": { "codexAgent": true, "crossReview": true },
  "storage": { "agent-cockpit.display": { "mode": "product" } },
  "steps": [
    { "do": "click", "selector": ".decision-card [data-answer-pick]" },
    { "do": "type", "selector": ".decision-card [data-answer-note]", "text": "画面の幅は 850px で撮る" },
    {
      "do": "screenshot",
      "name": "answer",
      "target": ".decision-card",
      "parts": {
        "decision.pick": ".decision-card [data-answer-pick]",
        "decision.note": ".decision-card [data-answer-note]",
        "decision.send": ".decision-card [data-send-answer]"
      }
    }
  ]
}
```

- `scenario`:`tools/manual/demo/` のシナリオの名前。
- `window`:ウィンドウの論理の大きさ。`width` の既定は 850 である。高さは、全体を撮る `screenshot` では内容の高さに合わせて伸ばす。
- `theme`:`dark` か `light`。ダッシュボードの配色の設定として `localStorage` に書く。
- `integrations`:連携の有無。デモの常駐サーバーへ渡す。
- `storage`:撮る前に `localStorage` に書く値。表示モード、並び順、前回見てからの設定のように、画面だけで持つ設定に使う。
- `steps`:クリック(`click`)、入力(`type`)、要素が現れるまでの待ち合わせ(`wait`)、撮影(`screenshot`)を順に行う。`selector` は文書の順で最初に一致した要素を指し、一致する要素が無ければ撮影を止める。
- `screenshot` の `target`:撮る範囲の要素。省くとページ全体を撮る。
- `screenshot` の `parts`:ガイドマップの札を付ける部品の鍵と、その要素の selector。撮影は、各部品の矩形を画像に対する座標で `.json` に書く。

部品を selector で指すのは撮影の定義の中だけにし、原稿は部品の鍵だけを持つ。
画面のクラス名や構造が変わったときに直す場所を撮影の定義に閉じ、原稿を直さずに済ませるためである。

### 撮影の実行

`npm run manual:capture -- [定義名...]` で撮る。
定義名を省くと、すべての定義を撮る。
撮影のスクリプト(`tools/manual/capture.js`)は、定義ごとに次の順で進める。

1. 一時ディレクトリを作り、デモの常駐サーバーを起動してシナリオを流し込む。
2. Edge か Chrome を `--headless=new`、一時のユーザーデータのディレクトリ、`--remote-debugging-port=0` で起動し、CDP につなぐ。ブラウザは環境変数 `MANUAL_BROWSER` で指定でき、無ければ Edge と Chrome の既定の場所を探す。
3. `Emulation.setDeviceMetricsOverride` で幅 850px、倍率 2 にし、`Emulation.setEmulatedMedia` で `prefers-reduced-motion: reduce` にする。作業中の点の点滅を止めるためである。
4. `localStorage` と時計を整えてからダッシュボードを開き、最初の状態の取得を待ってから手順を実行する。
5. 撮った画像と部品の矩形を `manual/img/<定義名>/` に書く。中身が前と同じファイルは書き換えない。
6. ブラウザと常駐サーバーを終了し、一時ディレクトリを消す。

撮影は開発機の普段のブラウザのプロファイルを使わない。
普段のプロファイルの `localStorage` と拡張機能が画面に混ざるのを避けるためである。

### 表示のパターン

実際の使い方を思い浮かべられるよう、要素の多い全体図に加えて、表示が変わる状態ごとに撮る。

| 撮るもの | 状態 |
|---|---|
| 全体図 | プロダクト別、種類別 |
| 判断事項 | デスクトップアプリで答える案内、回答欄(選んで指示を書いた)、送信済み、仮適用、解決済みを畳んだ |
| 許可待ち | 待ち始め、長く待たせている |
| PR | マージできる、条件が残る、積み直し待ち、衝突と解消の依頼、レビュー未実施とレビュー不要、確認欄を開いた、レビュー収束後マージを予約した、マージの結果 |
| 離席中 | 離席中にしたヘッダ、前回見てから |
| 経路の設定 | 2 つの連携がある、サブエージェントだけ、経路を変えた後の「変更前」の札 |
| 一覧 | セッションが無い、更新の無いセッションを隠した、プロダクトを畳んだ |
| 設定画面 | 設定画面の全体 |
| 配色 | ライトの全体図(表示の設定のページで配色の違いを示す) |

配色のパターン以外は、ダークで撮る。
全部の画像を両方の配色で撮ると、画像の量とコミットの量が 2 倍になるためである。

### 画像の規格

- 形式は PNG、倍率は 2 とする。幅 850px の全体図は 1700px の画像になる。
- 部品の矩形の `.json` は組み立ての材料で、配信しない。
- 1 枚の画像は 1MB 以下を目安にする。超えるときは、`target` で範囲を絞るか、シナリオの要素を減らす。

## 配信

常駐サーバーは `GET /manual/` 以下を次のように配る。

- `/manual/` と `/manual/<id>.html`、`/manual/assets/*` は `manual/dist/` から配る。`/manual/` は `index.html` を返す。
- `/manual/img/<定義名>/<名前>.png` は `manual/img/` から配る。
- 配る拡張子は `.html`、`.css`、`.js`、`.png` に限り、それ以外と、パスに `..` や区切りの重なりを含む要求は `404` にする。部品の矩形の `.json` を配らないためと、`manual/` の外を読ませないためである。
- 書き込みの口は作らない。秘密値は要らないが、全要求の `Host` の照合と、全応答に付ける共通のヘッダ(`cache-control: no-store`、`x-frame-options: DENY` など)はダッシュボードと同じにする。`no-store` により、組み立て直した後に古いページが見えることも無い。

## 画面からの導線

設定画面の下端のボタン列の左端に、「マニュアル」のリンクを置く。
画面の常時表示は増やさない。
設定画面を開いた人が次に知りたいのは設定の各項目の意味なので、飛び先は `settings` のページにする。

画面が持つのは、入口に飛び先の鍵を付けた URL(`/manual/#help-settings`)だけにする。
入口のスクリプトが、`site.json` の `helpAnchors` の表から該当のページと節へ移す。
画面がページの URL を持つと、ページを分けたり統合したりしたときに導線が壊れるためである。
飛び先の節には、見出しとは別に `help-<画面>` の固定の id を付ける。

リンクは新しいウィンドウで開く(`target="_blank"`、`rel="noopener"`)。
ダッシュボードの表示と状態を残したままマニュアルを読めるためである。

導線はモック([mock/index.html](../../mock/index.html))の設定画面にも同じ位置に足す。

## 検査

`npm run lint:manual` は次を調べる。

- **組み立ての結果**:原稿と画像から組み立て直した結果が、コミットした `manual/dist/` と一致する。原稿を直して組み立てを忘れたときと、結果を直接直したときを検出する。
- **画面の文言**:原稿で `<span class="ui">…</span>` で囲んだ文言が、`src/web/index.html` に文字列として現れる。画面の文言を変えて原稿が古くなったときを検出する。
- **画像**:原稿が指す画像があり、どこからも指されない画像が無い。撮影の定義ごとに画像がある。
- **ガイドマップ**:一覧の項目が指す部品の鍵が、その画像の矩形の一覧にある。
- **リンク**:ページ内とページ間のリンク先の節がある。`helpAnchors` の行き先の節がある。画面が持つ鍵がすべて `helpAnchors` にある。

検査は `npm test` からも呼び、テストと同じ機会に流す。
撮影はブラウザを要るので `npm test` には含めない。
