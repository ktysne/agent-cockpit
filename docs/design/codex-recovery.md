# Codex のセッションの復旧

Codex 対応の順序 7(#177)の設計である。
常駐サーバーを再起動したときに、Codex のセッションの行を Claude と同じ仕様で戻す。
計画と順序の正本は [2026-10-11-codex-rebuild.md](../handover/2026-10-11-codex-rebuild.md) にある。
Codex のセッション行の作りは [codex-registration.md](codex-registration.md) にある。

## 方針

Claude と同じ目的の処理と表示は、同じ仕様にする(開発者の決定)。
この資料は、Claude の今の仕様を既定とし、Codex で同じにできない点だけを「差」として決める。

## 範囲

Issue #177 は、cockpit が管理する app-server の配信台帳と親子対応を保存する旧設計で書かれている。
配信はフックで行い、app-server は作らない(計画書の決定済みの判断「配信の経路」)。
この資料は、常駐サーバーの再起動の前後で、Codex のセッションの行と、行に付く情報(タスク、判断事項、モデル名、再開の回数)を Claude と同じに保つことだけを扱う。

## 再起動の前後の今の挙動

確認用の常駐サーバーで、Claude と Codex のセッションを作って再起動し、比べた。

- タスクと判断事項は、どちらも保存から戻る。判断事項は、次の入力で Claude と同じ規則で閉じる。
- Claude の行は、生きているセッションのファイル(`~/.claude/sessions`)から、再起動の直後に戻る。ファイルにはセッションのプロセス ID があり、プロセスが終わってファイルが消えると、60 秒後に終了扱いになる。
- Codex の行は、次のイベントが届くまで出ない。その間は、待ちの判断事項もタスクも画面に出ない。
- Codex の行が戻っても、モデル名と再開の回数は消えている。

## 差と決定

### プロセス ID の記録

Codex にはセッションのファイルが無いので、Codex のフックから Codex 本体のプロセス ID を記録する。
実機(Codex 0.162.1 の `codex exec`、Windows)で、フックの親はフックごとに起動するシェル(`pwsh.exe`)で、その親の `codex.exe` はセッションの開始から終わりまで同じ ID だった。

- イベントの入口(`event.js codex`)は、`SessionStart` のときだけ、自分の親から 4 段までさかのぼり、プロセス名が `codex` か `codex.exe`(大文字と小文字を区別しない)の最初のプロセスの ID を、イベントの `codexPid` に載せる。見つからなければ載せない。
- さかのぼるのは `SessionStart` のときだけにする。親をたどる問い合わせは Windows で 1 秒近くかかり、ツールのたびに行うとフックが遅くなるためである。
- 常駐サーバーは、`codexPid` を正の整数のときだけ受け付ける。

### 保存

常駐サーバーは、Codex のセッションごとに、次の値を保存ファイル(`store.json`)に持つ。

- プロセス ID、`cwd`、モデル名、再開の回数、最後に記録した時刻。
- 会話の本文、ツールの入出力、秘密値は持たない。
- 件数に上限を置き、超えたら最後に記録した時刻の古いものから捨てる。

保存ファイルを書くのは常駐サーバーの 1 プロセスだけである(起動の排他は `start.lock`)。別のプロセスが同時に書くと、片方の記録が上書きで消えるため。

### 行の戻し方と終わらせ方

保存した Codex のセッションを、Claude のセッションのファイルと同じ一覧に混ぜて扱う。

- セッションのファイルを読み直すたび(10 秒ごと)に、保存した Codex のセッションのうち、プロセスが生きているものを一覧に加える。
- 再起動の直後は、一覧から行を作る。状態は Claude と同じく「不明」で、次のイベントで更新する。
- 一覧から消えたセッションは、Claude と同じく、イベントで作った行なら 60 秒後に終了扱いにし、一覧にだけある行(再起動の後にまだイベントが届いていない行)はその時点で消す。プロセスが終わったら、そのセッションの保存も捨てる。
- 戻した行には、保存したモデル名と再開の回数を出す。再起動の後のイベントにモデル名があれば、時刻の順で最後のものを出し、無ければ保存したモデル名を出す。再開の回数は、保存した回数に、再起動の後の再開を足す。
- 最後に記録した時刻は、戻した行の無操作の判定(「無操作で隠す」設定)に使う。保存の回数を抑えるため、1 分以上進んだときだけ更新する。
- `codexPid` を記録できなかったセッションは、今と同じく、次のイベントまで行を出さない。

### 会話の終わりと SessionEnd

Codex の TUI とデスクトップは画面だけを担い、会話は共有の常駐プロセス(TUI は `codex app-server --managed-daemon`、デスクトップはアプリの `app-server`)が動かす。
そのため、会話を終えてもフックを動かすプロセスは残り、プロセスの生死では行を終わらせられない。

- TUI を `/exit`、Ctrl+C、ウィンドウを閉じる操作のどれで終えても、約 1 分後に常駐プロセスが会話を閉じ、そのときに SessionEnd が届いて行が閉じる(実機で確かめた)。この遅れのあいだ、行は待機中のまま残る。
- デスクトップで会話をアーカイブしても、SessionEnd は届かない(実機で確かめた)。

会話を閉じると、Codex は `<CODEX_HOME>/thread-writer-locks/<thread の ID>.lock` を消す(TUI でもデスクトップでも確かめた)。
これを使い、一度でもロックを見た会話のロックが消えたら、プロセスが生きていても一覧から外し、Claude と同じ不在の扱いで 60 秒後に行を終わらせる(開発者の決定)。

- ロックを見たことは復旧の記録に持ち、常駐サーバーの再起動の後も効かせる。ロックが消えたら、記録も消す。
- ロックを作らない実行(`codex exec`)は、今までどおりプロセスの生死だけで扱う。
- 行が終わった後に同じ会話のイベントが届けば、行は戻る。
- `thread-writer-locks` は公開仕様ではない。読めないときはロックで判断しない。形が変わっても、行がアプリを閉じるまで残るだけで済む。

## 範囲の外

- Issue #177 の配信台帳(送信中、受付、適用、未確認の区別と、再送の禁止)と、委譲した実行の親子対応の保存は、app-server を使う旧設計の要件である。回答と通知は、Claude と同じく、保存した `deliveredAt` と `reflectedAt` で扱う。
- 委譲した Codex(セッション行が無い)は対象にしない。
