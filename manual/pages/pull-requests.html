PR とマージ

セッションが作った PR は、プロダクトのカードの プルリクエスト の欄に、スタックの形で並びます。 条件がそろった PR は、この欄から、スタックの一番下のものだけをマージできます。 このページでは、PR の登録と取得、行の見方、マージできます の条件、マージの確認欄、レビュー収束後マージの予約、レビュー不要の記録、衝突の解消の依頼、マージの結果を説明します。

積み上げた PR を下から順にマージする流れは、積み上げた PR を順にマージするで順に説明しています。

PR の登録

欄に出るのは、セッションに結び付けて登録した PR と、その PR とスタックでつながるオープンの PR です。 登録は、次のどれかで行われます。

  • セッションが gh pr create を実行し、その出力に PR の URL がある。自動で登録されます
  • セッションが GitHub の MCP サーバーのツール(create_pull_request)で PR を作り、その応答に PR の URL がある。自動で登録されます
  • メインセッションが、Agent Cockpit のツール cockpit_add_pr に PR の URL を渡す。手で作った PR のように、上の 2 つで登録されなかった PR に使います

URL は https://github.com/<owner>/<repo>/pull/<番号> の形でなければ登録されません。 PR は、登録したセッションのプロダクトの欄に出ます。

登録していない PR でも、登録した PR とスタックでつながっていれば、行に出ます。 ただし、その PR にはクロスレビューの行も マージする のボタンも出ません。 クロスレビューの状態を読む作業ツリーが分かるのは登録したセッションだけで、マージの操作も、登録したセッションに結び付くためです。

登録した PR が 1 件も無いプロダクトでは、プルリクエスト の見出しに「(0 件)」と出ます。 設定の 終わったものを非表示にする がオン(既定)のときは、続けて オープンの PR はありません と出ます。

登録の詳細

gh pr create の出力や GitHub の MCP ツールの応答に PR の URL が複数あるときは、最初の 1 件を登録します。 登録は常駐サーバーの保存先に保存するので、常駐サーバーを再起動しても残ります。

GitHub からの取得

PR の状態は、常駐サーバーが GitHub CLI(gh)で GitHub から取得します。 gh に保存された認証を使い、環境変数 GH_TOKEN などは渡しません。 各リポジトリの枠の見出しに、最後に取得できてからの時間が GitHub から の形で出ます。

取得し直すのは、次のときです。

  • 常駐サーバーを起動した直後と、そのあとの 60 秒ごと
  • PR を登録した直後
  • セッションが、git push か gh pr で始まるコマンドを実行した後(失敗したときも含みます)
  • マージ、レビュー収束後マージの予約、衝突の解消の依頼、画面からのレビュー不要の記録を行う直前

最後の操作の直前の取得は、画面に出ている状態が古くても、操作を最新の状態で判定するためです。

GitHub CLI が使えないとき

gh が見つからないとき、認証や通信に失敗したときは、リポジトリの見出しの下に赤い枠でエラーが出ます。 一度も取得できていない PR の行は出ません。 前に取得できていたときは、そのときの行が残り、枠が加わります。

エラーの原因は、次のどれかの文で出ます。

  • 「gh コマンドが見つかりません」：gh が入っていないか、常駐サーバーの PATH にありません
  • 「gh を実行できません」：gh の実行を OS が許可していません
  • 「gh の取得がタイムアウトしました」：gh の 1 回の実行が 20 秒で終わりませんでした
  • 「gh の認証、通信、または取得結果を確認してください」：上のどれでもない失敗です。gh の認証が切れているときや、通信できないときがこれに当たります

この文の前に、「PR の一覧を取得できません。」のように、取得できなかった対象が付きます。 マージ済みの PR の一覧や、PR 1 件の状態、積み直しの確認が取得できないときも、同じ形で出ます。

スタックの表示

PR の base ブランチが別の PR の head ブランチになっているとき、この 2 つの PR は積み上がった関係(スタック)にあります。 スタックは、base が既定ブランチの PR を一番下にして、その直上の PR を 1 段下げて入れ子で並べます。 登録した PR とつながる PR は、すべて同じスタックに出ます。

スタックの一番下以外の PR は、マージできません。 下の PR がマージされると、その直上の PR が一番下になります。

スタックの組み立ての詳細

オープンの PR の中から、base ブランチ名が別の PR の head ブランチ名と一致する PR を、その PR の上に積みます。 登録した PR を起点に、base と head でつながる PR をたどり、つながった PR をすべて出します。

base が既定ブランチでも、オープンの PR の head ブランチでもない PR は、マージできない理由 に「base の <ブランチ名> に対応する PR が見つからない」と出て、マージできません。

PR の行の札

PR の行は、題、状態の札、head と base、CI とレビューの札、クロスレビューの行、待ちの行で構成します。 下の図は、マージ操作はできるが、条件が残っている PR の行です。

CI とレビューの札

CI の札は、PR のチェックの結果を示します。

  • CI 成功：すべてのチェックが成功しています。チェックが 1 つも無い PR も、この札です
  • CI 実行中：実行中か、待機中のチェックがあります
  • CI 失敗：失敗、エラー、取り消し、時間切れなどで終わったチェックがあります。実行中のチェックが残っていても、失敗が 1 つでもあればこの札です

GitHub のレビューの札は、PR の承認の状態を示します。

  • 承認済み：必要な承認がそろっています
  • 承認待ち：承認が必要で、まだそろっていません
  • 変更要求：変更を求められています
  • 承認は任意：リポジトリが承認を求めていません

そのほかの札

CI とレビューの札の後ろに、PR の状態によって次の札が加わります。 下の図は、その札が出る PR の行です。

図に無い札が 1 つあります。 base を で始まる札は、ダッシュボードが、下の PR をマージするときに base を既定ブランチへ付け替えた PR に付きます(マージの結果)。

積み直し

スカッシュかリベースでマージすると、下の PR の元のコミットが、既定ブランチに別のコミットとして入ります。 下の PR のコミットは、その上の PR のブランチにも残ったままなので、上の PR の差分に、すでに既定ブランチに入った内容が重なります。 この状態の PR に 積み直しが必要 が付き、積み直し待ちとしてマージできなくなります。

積み直しは、セッションが行います。 上の PR を既定ブランチの上に積み直して push すると、札が消えます。 ダッシュボードからマージしたときは、積み直しの依頼をセッションに送ります(マージの結果)。

積み直しの判定の詳細

オープンの PR ごとに、既定ブランチとの差分に含まれるコミットを取得し、マージ済みの PR の head のコミットが含まれているかを調べます。 含まれていれば、積み直しが必要です。

差分やマージ済みの PR の一覧を取得できないとき、結果が取得の上限で切れて全件を確かめられないときは、確かめられない扱いにします。 この PR には「積み直しが必要か確かめられない」と出て、マージできません。

マージできない理由と待ち

マージ操作ができない PR には、マージできない理由 の行が出ます。 理由は、次の順に調べ、最初に当たった 1 つを出します。

  • 「リポジトリ設定を取得できません」：既定ブランチを取得できていません
  • 「base の <ブランチ名> に対応する PR が見つからない」：base が既定ブランチでも、オープンの PR の head でもありません
  • 「下の #<番号> のマージ待ち」：スタックの一番下の PR ではありません
  • 「base を <既定ブランチ> に付け替える必要がある」：下の PR がマージされたのに、この PR の base が既定ブランチに付け替わっていません
  • 「ドラフト」
  • 「積み直し待ち」：積み直しが済んでいません
  • 「積み直しが必要か確かめられない」
  • 「コンフリクトあり」
  • 「変更を求められている」：GitHub のレビューの札が 変更要求 です
  • 「レビューの承認待ち」：GitHub のレビューの札が 承認待ち です

どれにも当たらない PR は、マージ操作ができます。 CI とクロスレビューは、マージ操作ができるかどうかの判定には含めません。 この 2 つのうち、設定で選んだ条件を満たしていないものは、待ち: の行に出ます(「マージできます」の条件)。

クロスレビューの行

クロスレビュー の行は、ai-cross-review のクロスレビューが、この PR の head のブランチで何往復進んだかと、その結論を示します。 PR を登録したセッションの PR にだけ出ます。 状態の札は、次のどれかです。

  • レビュー済み：最後の結論が「収束」で、その結論を出した時点のコミットが、PR の今の head と同じです
  • 収束の後に変更あり：収束した後に push があり、今の head が収束したコミットと違います。収束したコミットの 7 桁が続きます
  • 指摘の対応中：最後の結論が「指摘に対応中」です
  • 開発者の判断待ち：最後の結論が halted(停止)で、開発者の判断を待って止まっています
  • 往復目の結論待ち：「2 往復目の結論待ち」のように、前の往復の結論は記録されていますが、新しい往復の結論がまだ記録されていません
  • この head をレビューに回した：結論は記録されておらず、最後にレビューに回したコミットが今の head と同じです
  • レビューの後に変更あり：結論は記録されておらず、最後にレビューに回した後に push があります
  • レビュー未実施：この PR のブランチに、クロスレビューの記録がありません
  • レビュー不要：クロスレビューを使っていないか、レビュー不要と記録されています(レビュー不要の記録)
  • 状態を確認できない：記録を読めませんでした
  • head を確かめられない：PR の今の head を取得できていません
クロスレビューの状態を読む場所の詳細

状態は、PR を登録したセッションの作業ツリーにある、ai-cross-review の状態ファイル(.cross-review-state.json)から、PR の head のブランチの記録を読みます。 同じブランチを別の作業ツリーでチェックアウトしているときは、その作業ツリーの記録も読み、記録のあるものと、今の head で収束しているものを選びます。

作業ツリーに tools/cross-review.js が無いリポジトリは、クロスレビューを使っていないとみなし、レビュー不要 と出します。 この場合は、レビュー不要にする のボタンは出ません。 状態ファイルが無くても、tools/cross-review.js があれば レビュー未実施 です。

「マージできます」の条件

PR の状態の札は、2 段階の条件で決まります。

  • マージ操作は可能：マージの操作ができる PR です。スタックの一番下で、ドラフト、積み直し待ち、コンフリクト、GitHub のレビュー待ち(変更要求 と 承認待ち)のどれでもありません。灰色の背景で出ます
  • マージできます：マージの操作ができ、さらに設定で選んだ条件を満たす PR です。緑の背景で出ます

設定の 「マージできます」と出す条件 で、さらに満たす条件を選びます(設定の項目)。

  • マージの操作ができる：マージの操作ができれば、マージできます と出します
  • CI も通っている(CI が無ければ問わない)：マージの操作ができ、CI 成功 のときに出します
  • クロスレビューも済んでいる(不要としたものを含む)：マージの操作ができ、CI 成功 で、クロスレビューが レビュー済み か レビュー不要 のときに出します。既定の選択です

条件が残っている PR は マージ操作は可能 のまま、待ち: の行に、満たしていない条件が出ます。 この PR も、確認欄から手でマージできます。 確認欄の先頭に、満たしていない条件を警告します(マージする)。

マージできます と出ている PR の数は、画面上部の マージできる PR の札、プロダクトのカードの見出し、リポジトリの枠の見出しに出ます(件数の札)。 マージする のボタンの無い PR は、数えません。

条件の判定の詳細

待ちの行に出る言葉は、次のとおりです。

  • CI：「CI が失敗」「CI 実行中」
  • クロスレビュー：「クロスレビュー未実施」「クロスレビュー対応中」「クロスレビューが開発者の判断待ち」「クロスレビュー後に push あり」「クロスレビューの状態を確認できない」

クロスレビューが済んでいるとみなすのは、最後の結論が「収束」で、その往復が今の往復と一致し、結論を出したコミットが PR の今の head と同じときです。 クロスレビューを使っていないリポジトリの PR は、レビュー不要として済んでいるとみなします。

マージする

マージは取り消せません。 ダッシュボードに、マージした PR を元に戻す操作はありません。 確認欄の方式、ブランチの削除、未達条件の警告、照合する head の SHA を読んでから、マージを実行 を押します。 ダッシュボードがマージを実行するのは、開発者が確認欄で実行を押したときと、開発者が予約したレビュー収束後マージの条件がそろったときだけです。

マージするには、マージする を押して確認欄を開き、マージを実行 を押します。 確認欄は、PR の行の下に出ます。 やめる を押すと、何もせずに閉じます。

確認欄の既定は、次のとおりです。

  • 方式：同じリポジトリで最後にマージまたは予約した方式です。初めてのリポジトリでは、許可された方式のうち、マージコミット、スカッシュ、リベース の順で最初のものです。方式が 1 つしか許可されていないときは、リポジトリで許可されている方式です と出ます
  • マージ後にリモートブランチを削除する：入っています
  • レビュー収束後マージ：設定の レビュー収束後マージを既定でオンにする に従います(既定はオフです)

確認欄で選んだ内容は、ページを開いている間だけ覚えています。 ページを開き直すと、既定に戻ります。

ブランチの削除の詳細

リポジトリが、マージしたブランチを GitHub 側で自動的に削除する設定のとき、マージ後にリモートブランチを削除する は出ません。 ブランチの削除は GitHub に任せます。 結果の行には「ブランチの削除は GitHub の自動削除の設定に任せた (結果は未確認)」と出ます。

fork から出した PR の head のブランチは、登録先のリポジトリから削除できません。 チェックは外れて押せなくなり、fork のブランチは登録先から削除できません と出ます。

ブランチは、マージが済んだ後に、常駐サーバーが GitHub の API で削除します。 すでに削除されているときは、削除できたものとして扱います。 削除に失敗したときは、マージ済みのまま、結果の行に警告が出ます。

マージの前に確かめること

確認欄を開いた時点から実行するまでに PR が変わっても、意図しないコミットをマージしないために、常駐サーバーは次を確かめます。

  • 実行を押した時点で、GitHub から PR の状態を取り直します
  • 画面で見ていた head のコミットが、取り直した head と同じです。違うときは、マージせずに、「表示していた head SHA と現在の head SHA が異なります。状態を確認してください」と出します
  • 選んだ方式を、リポジトリが許可しています
  • PR が、スタックの一番下で、マージ操作ができる状態です。CI とクロスレビューは確かめません。確認欄に警告を出すだけで、実行は止めません

確かめた後、gh pr merge には、画面で見た head のコミットを --match-head-commit で渡します。 取り直してから gh pr merge を呼ぶまでの間に push があっても、GitHub がマージを断ります。

マージの手順の詳細

実行を押すと、常駐サーバーは次の順に進めます。

  1. GitHub から PR の状態を取り直し、上の条件を確かめます
  2. 直上の PR があれば、その base を既定ブランチに付け替えます。方式にかかわらず行い、1 件でも失敗したらマージしません
  3. もう一度取り直して、条件を確かめます
  4. gh pr merge を実行します
  5. PR の状態を読み、マージ済みであることを確かめます
  6. ブランチの削除を選んだときは、ブランチを削除します
  7. PR を登録したセッションに、結果を知らせます(マージの結果)

同じ PR の操作が進行中のときは、後から押した操作を断り、「操作が進行中です」と出します。

失敗したときは、PR の行の下に理由が出ます。 付け替えが済んだ後に失敗したときは、付け替えが済んでいることも書きます。 失敗の知らせは 1 分で消えます。 確認欄は残るので、状態を確認してから マージを実行 をもう一度押せます。

gh pr merge が成功しても PR がマージ済みにならないときは、マージキューに入ったとみなします。 PR の行に マージキューに追加済み (未マージ) と出ます。 マージされた後は、画面の外でのマージとして扱うので、方式は不明になり、ブランチは削除しません。 GitHub のキューから外れたときは、キューから外れた を押すと、マージの操作に戻ります。

スタックの途中をマージする

直上に PR のあるスタックの一番下を、スカッシュ か リベース でマージするときは、確認欄に、上の PR に元のコミットが残るため、セッションに積み直しを依頼する旨の警告が出ます。

レビュー収束後マージ

レビュー収束後マージ は、クロスレビューが収束し、条件がそろうまで待ち、そろった時点で常駐サーバーがマージする予約です。 クロスレビューの最中に、方式とブランチ削除を決めておけます。 予約はダッシュボードを開いていなくても実行されます。

確認欄で レビュー収束後マージ を入れると、ボタンが 予約する に変わります。 照合する head SHA は、PR の今の head ではなく、クロスレビューの収束記録のコミットになります。

予約すると、PR の行の マージする は 予約を取り消す に変わり、行が予約中の背景になります。 予約中の札には、方式、予約した時刻、まだ満たしていない条件が出ます。

常駐サーバーは、PR の状態を取得するたびに予約を確かめ、次の条件がすべてそろったときに、通常のマージの手順でマージします。

  • クロスレビューの最後の結論が「収束」で、その往復が今の往復と一致し、結論を出したコミットが PR の今の head と同じである。レビュー不要 の記録だけでは、実行されません
  • CI が成功している
  • GitHub のレビューが 承認済み である。承認は任意 のリポジトリの PR は、承認が付くまで実行されません
  • PR が、スタックの一番下で、ドラフトでもコンフリクトでもなく、マージ操作は可能 である。選んだ方式を、リポジトリが許可している

収束した後に push があって、今の head が収束したコミットと違うときは、予約は残ったまま、新しい head の収束を待ちます。 gh pr merge には、収束記録のコミットを --match-head-commit で渡します。

常駐サーバーが止まっている間に条件がそろったときは、起動後の最初の取得で実行します。 予約は常駐サーバーの保存先に保存するので、再起動しても残ります。

予約が取り消されるとき

予約は、次のときに取り消されます。

  • 予約を取り消す を押したとき
  • PR が、マージされずにクローズされたとき
  • クロスレビューの最後の結論が halted(停止)になったとき
  • マージを実行して、PR がマージキューに入ったとき(以降は、方式を不明として扱い、ブランチは削除しません)

取り消されると、リポジトリの枠に、PR へのリンクと取り消した理由が出ます。 PR を登録したセッションにも、同じ内容を知らせます。

取り消しの知らせは、記録時刻から 1 分たつか、同じ PR を予約し直すと消えます。 取り消す前に PR が画面の外でマージされたときは、予約が消えるだけで、取り消しの知らせは出ません。

レビュー不要の記録

クロスレビューを省く PR は、レビュー不要と記録できます。 記録した PR は、クロスレビューも済んでいる(不要としたものを含む) の条件を満たします。 ただし、レビュー収束後マージ は、クロスレビューの収束記録が要るので、レビュー不要の記録だけでは実行されません。

記録は、次の 2 つの方法で行います。

  • PR の行の レビュー不要にする を押す。記録する理由は、画面からの記録だと分かる文になります。このボタンは、レビュー未実施や変更あり、対応中のように、クロスレビューの状態が黄の札のときだけ出ます。レビュー済み などレビューが要らない状態では、記録しても何も変わらないので出しません
  • PR を登録したセッションが、Agent Cockpit のツール cockpit_skip_review に、リポジトリ、PR の番号、今の head のコミット、理由を渡す。そのセッションが登録した PR にだけ使えます

記録すると、クロスレビューの状態の札が レビュー不要 に変わり、ボタンは レビュー不要を取り消す になります。 レビュー不要 の札にマウスを載せると、記録した理由が出ます。 レビュー不要を取り消す を押すと、記録を消します。

記録は、記録した時点の head にだけ有効です。 push で head が変わると、記録は無効になり、札が元の状態に戻ります。 記録する時点でも、常駐サーバーが PR の head を取り直し、画面やセッションが見ていた head と違えば、記録しません。

衝突の解消の依頼

コンフリクトのある PR には、コンフリクト解決 のボタンが出ます。 押すと、PR を登録したセッションに、衝突の解消を依頼する確認欄が開きます。 ダッシュボードは、PR のブランチを変えません。作業はセッションが行います。

依頼を受けたセッションには、次の内容が届きます。

  • PR の番号と URL
  • base のブランチを取り込んで衝突を解消し、検証してから push すること
  • PR をマージしないこと
  • 衝突を解消できないときは、その理由を報告すること

依頼は、PR を登録したセッションのうち、終了していないものへ送ります。 届く経路は、判断事項への回答と同じです(回答が届く経路)。

依頼に失敗したときは、PR の行に理由が出ます。 失敗の知らせは 1 分で消えます。 確認欄は残るので、状態を確認してから 依頼を送る をもう一度押せます。

依頼を送ると、PR の行に、依頼した時刻と依頼先が出て、ボタンは もう一度依頼する に変わります。

依頼済みの表示は、PR の head が依頼した時点から変わると消えます。 衝突が解消されてコンフリクトの札が消えたら、PR の行からマージします。 依頼の記録はメモリーにだけ置くので、常駐サーバーを再起動すると消えます。

依頼先のセッションが無いときは、ボタンが押せなくなり、衝突の解消を依頼できない理由 が出ます。 PR を登録したセッションが無いときと、登録したセッションがすべて終了しているときです。

マージの結果

マージが済むと、PR の枠に結果の行が出ます。 スタックの直上の PR は、base が既定ブランチに付け替わり、一番下の PR になります。

結果の行には、次の内容が出ます。

  • マージの方式
  • ブランチを削除したか。削除しなかったときと、GitHub の自動削除に任せたときは、その旨
  • 直上の PR の base を付け替えたときは、付け替えた PR の番号
  • ブランチを削除できなかったときなどの警告

結果の行は、ページを開いている間だけ出ます。 ページを開き直すと消えます。 設定の マージの結果を隠すまで (分) に指定した時間がたつと、警告のない行は自動で隠れます。初期値は 5 分で、1〜60 分の整数を指定できます。 ブランチ削除などの警告がある行と、予約時に確認した head と異なる head がマージされた行は自動で隠れず、閉じる を押すまで残ります。 レビュー収束後マージの結果は常駐サーバーに保存され、閉じる を押すと閉じた状態も保存されます。マージ履歴が 24 時間で整理されると結果も消えます(マージの結果を隠すまで)。

セッションへの知らせ

マージを検出すると、常駐サーバーは、PR を登録したセッションと、直上の PR を登録したセッションに知らせます。 「PR #41 が main に入りました。方式: スカッシュ。」のような文です。 届く経路は、判断事項への回答と同じです(回答が届く経路)。

スカッシュかリベースでマージしたときは、直上の PR ごとに、git rebase --onto で積み直して push する依頼が続きます。 マージコミット でマージしたときは、積み直しの依頼はありません。

ダッシュボード以外でマージした PR も、取得の中で検出して知らせます。 この場合は方式が分からないので、「方式は取得できませんでした」と書き、積み直しの依頼とブランチの削除は行いません。

マージ済みの一覧

リポジトリの枠の下端に、マージ済み (24 時間) として、GitHub でマージされてから 24 時間以内の PR が、新しい順に並びます。常駐サーバーを止めていた間にマージされた PR も、マージされた時刻から数えます。 各項目は、PR の番号に、マージした時刻と方式が続きます。 レビュー収束後マージで実行したものには、予約で自動 が付きます。 5 件を超える分は、「古いマージ済みを表示」のボタンで開きます。

この一覧は、設定の 終わったものを非表示にする がオフのときだけ出ます。 ただし、予約のときに確認したコミットと違うコミットがマージされた PR は、設定にかかわらず、警告つきで出ます。 マージされずにクローズした PR は、同じ設定がオフのときに、クローズ済み として並びます。
